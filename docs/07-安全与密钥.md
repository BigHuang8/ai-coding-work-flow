# 安全与密钥

AI 让「批量写入」变得很容易，也让「批量泄漏」变得很容易。本文是硬性约束，不接受例外。

> 配图见 [`assets/secrets.png`](../assets/secrets.png)：零入库清单、配置放哪、提交前三问、泄漏应急与 AI 边界。

## 一、零入库清单

以下内容**永远不得进入版本库**（含文档、注释、示例、技能说明、测试数据、截图）：

- 数据库账号与口令
- API Key、AppSecret、签名密钥、盐值
- 各类 Token、Cookie、Session ID
- 证书私钥（`.pem` / `.key` / `.p12` / `.jks`）
- 真实用户数据：手机号、身份证号、银行卡号、保单号、地址
- 内网地址与拓扑（非必要不写；必须写时用占位符）
- 生产环境连接串、端口、账号

## 二、正确做法

### 配置用环境变量

```bash
# .env.example（入库，只放占位符）
DB_HOST=localhost
DB_PORT=3306
DB_NAME=app
DB_USER=app_user
DB_PASSWORD=change-me
API_KEY=your-api-key-here
```

```bash
# .env（不入库，已由 .gitignore 排除）
DB_PASSWORD=<真实口令>
```

### 文档里怎么写

```markdown
## 启动步骤

1. 复制 `.env.example` 为 `.env`
2. 填入本地数据库口令（向维护者索取，不要写进本文件）
3. 执行 `npm run dev`
```

**禁止**在文档里写「默认口令是 xxx，测试环境也是这个」。

### 在 AI 对话里

- 不要把真实口令粘进对话。需要 AI 写连接代码时，用占位符或环境变量名。
- 如果已经粘过：视为已泄漏，按第五节处理。
- 让 AI 生成示例配置时，明确要求「只写占位符」。

## 三、提交前检查

本地钩子与 CI 会扫描常见的敏感模式（见 `scripts/check-docs.mjs`），但它只能拦住格式明显的泄漏。**不要依赖扫描器代替自查。**

自查三问：

1. 这次改动里有没有出现「看起来像真的」的密钥？
2. 有没有把本地 `.env` 的内容贴进文档或测试？
3. 截图里有没有账号、手机号、真实姓名？

## 四、权限最小化

| 实践 | 说明 |
| --- | --- |
| 本地开发用只读账号 | 需要写权限时显式申请，不用生产账号 |
| 生产变更走审批 | 不允许个人直连生产库执行 DDL |
| 密钥按环境隔离 | 测试环境密钥不能用于生产 |
| 定期轮换 | 至少每半年轮换一次；人员离职即轮换 |
| AI 工具最小授权 | 不给 AI 直接操作生产环境的权限 |

## 五、泄漏应急响应

发现密钥进入版本库时，按顺序执行，**不要先删文件了事**：

1. **立即轮换该密钥**。历史提交仍在，删文件不能撤销泄漏。
2. **确认暴露范围**：哪些分支、哪些远程、是否已推送、是否被流水线日志记录。
3. **清理历史**：使用 `git filter-repo` 或平台提供的敏感信息清除功能（由维护者执行，并通知所有协作者重新克隆）。
4. **记录**：在 `MEMORY.md` 记一行（描述事件与处理，**不要记录密钥本身**）。
5. **补门禁**：分析为什么没被拦住，补规则或补检查项。

## 六、AI 相关风险

| 风险 | 应对 |
| --- | --- |
| 把敏感代码或数据上传到外部服务 | 遵守公司数据分级要求；敏感代码不喂给外部模型 |
| AI 生成的代码引入依赖投毒 | 新增依赖需显式评审，锁定版本与来源 |
| AI 生成的配置默认开启调试或宽松权限 | 配置类改动必须走 ④ 验证并留证据 |
| 技能文件里沉淀了口令 | 技能评审时强制检查，见 [技能体系](03-技能体系.md) |
| 证据截图包含真实用户数据 | 截图前用假数据；必须用真实数据时打码 |

## 七、检查清单

提交前逐条确认：

- [ ] 没有密钥、口令、Token 进入改动
- [ ] 没有真实用户数据进入改动
- [ ] 示例配置只有占位符
- [ ] 截图已脱敏
- [ ] 新增依赖已评审并锁定版本
- [ ] 涉及生产配置的改动已写明回滚方式
