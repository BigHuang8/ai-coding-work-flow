# 常见问题

## 一、流程太重怎么办

**先确认是不是真重。** 大多数「重」来自两种情况：

1. **该裁剪没裁剪。** 一行文案修改确实不需要写设计稿，见 [工作流总览](01-工作流总览.md) 的裁剪规则。
2. **文档写得过长。** `spec/` 页超过 200 行、验收报告超过 100 行，说明在写作文而不是在留证。留证要的是命令与输出，不是散文。

如果裁剪后依然觉得重，请提 RFC：说明哪一步实际没产生价值、建议怎么改。**不要私下跳过**，那会让门禁形同虚设。

## 二、需求一直在变，还要写 SPEC 吗

要写，但写的方式要变：

- 只固化**当前已确认**的部分，未确认的写进「待确认项」并写明谁来确认。
- 需求变更**直接改 `SPEC.md`**，并在 `MEMORY.md` 记一行变更原因。不要新建一堆平行文档。
- `spec/` 页保留**原始描述**不回改，这样事后能看出需求是怎么演进的。

## 三、AI 说「已完成」但其实是错的

这是最常见的失效模式。三个防御手段：

1. **要求 AI 先说要跑什么命令、预期看到什么**，再执行。预期错了当场就能发现理解偏了。
2. **要求原样贴回输出**。禁止「验证通过」这类无证据结论。
3. **失败时不立刻让 AI 改代码**，先让它解释失败原因与判断依据。直接改容易变成「打补丁掩盖问题」。

参见 [验收与证据留档](06-验收与证据留档.md) 第六节。

## 四、多人同时用 AI 改同一个模块，怎么不打架

1. **按文件划分**任务边界，见 [团队协作与角色](02-团队协作与角色.md) 第四节。
2. **接口先行**：先把签名与数据结构定下来提交，再并行实现。
3. **契约类文件单一写入者**：同一时间只允许一个人改 `docs/API_CONTRACT.md`。
4. 分支寿命不超过 3 个工作日，每天同步主干。

## 五、外部技能要不要拷进仓库

**不要拷贝正文。** 拷贝会产生两套各自漂移的副本。正确做法：

- 外部技能放 `.agents/skills/`，来源与哈希记在 `skills-lock.json`。
- 需要「改写以适配本项目」时，在 `skills/` 下写一个**自己的**技能，在其中引用外部技能并说明差异。
- 详见 [技能体系](03-技能体系.md)。

## 六、AI 读不到最新文档怎么办

上下文是「拉取式」的，AI 只会读你让它读的，或入口文件引用到的。所以：

1. 新文档必须**被 `AGENTS.md` 引用**，否则等于不存在。
2. 关键约束要写进 `AGENTS.md` 的硬性规则，而不是只躺在某个深层文档里。
3. 每次改完规范，顺手确认引用链没断——`node scripts/check-docs.mjs` 会检查链接有效性。

## 七、密钥不小心提交了怎么办

按 [安全与密钥](07-安全与密钥.md) 第五节执行。**第一件事是轮换密钥，不是删文件。** 历史提交仍在远程仓库里，删文件撤销不了泄漏。

## 八、评审者没时间评审

- 约定 24 小时响应 SLA，写进 `docs/02-团队协作与角色.md`。
- 超时由维护者指定替代评审者。
- 不允许「因为没人评审就直接合并」——那是把风险转移到线上。
- 一个人维护的项目：采用 30 分钟冷却期 + 自审清单填写记录。

## 九、模板里的文档和项目里已有的文档重复了

正常。接入时的处理原则：

| 情况 | 处理 |
| --- | --- |
| 项目已有自己的规范文档 | 让 `AGENTS.md` 指向它，不迁移、不改写 |
| 项目文档与本模板规范冲突 | 以项目实际为准，但在 `MEMORY.md` 记一行说明为何不一致 |
| 项目文档已过时 | 标记归档，不要直接删除，避免丢失历史决策 |

模板提供的是**方法与骨架**，不是必须逐字照搬的教条。

## 十、什么时候该改模板本身

出现以下信号时，说明模板需要演进：

- 某个门禁连续 3 个月没拦下过任何问题 → 考虑删除或简化
- 同一类问题在评审中反复出现 → 补一条规范或加一个自动检查
- 团队反复抱怨某一步 → 先做一次复盘，再改规则，不要凭感觉改

变更流程：提 RFC（现状 / 痛点 / 备选方案 / 影响面）→ 维护者裁定 → 改文档 + 改门禁 + 记 `CHANGELOG.md`。

## 十一、金额和时间到底该用什么字段类型

三条硬约定，不要临场发挥：

- **金额**用 `DECIMAL(18,2)`；需要更细粒度时用整数存「分」，并在字段注释里写明单位。禁止 `FLOAT` / `DOUBLE`——浮点会让对账长期对不平。
- **时间**用 `DATETIME(3)`，不用 `TIMESTAMP`（时区转换与 2038 问题）；全库统一，不要一半存时间戳一半存字符串。
- **前端传金额用字符串**：JavaScript 的数字是浮点，超过 15 位有效数字就会失真。

完整类型对照见 [数据库设计与建表规范](15-数据库设计与建表规范.md) 第五节。

## 十二、到底要不要建外键

- **默认不建物理外键**：并发写入、批量迁移、分库分表时外键都会成为障碍，一致性由应用层 + 唯一索引保证。
- **但唯一约束必须落库**（`uk_` 唯一索引）。业务唯一性靠应用层「先查再插」，在并发下必然被击穿——这不是风格问题，是正确性问题。
- 低频写入的配置类表可以建外键，但要在设计说明里写清理由与级联策略。

理由与替代方案见 [数据库设计与建表规范](15-数据库设计与建表规范.md) 第七节。

## 十三、项目用的技术栈模板里没有规范，怎么办

先让脚本说清楚缺口，再动手：

```bash
node scripts/detect-stack.mjs          # 输出「已启用 / 装箱未启用 / 缺口」三类清单
node scripts/detect-stack.mjs --check  # 缺口会提示，--strict 时直接失败
```

缺口**不允许放着不管**——AI 会按自己的偏好发明约定，同一个技术栈很快出现两套写法。处理方式：

1. 在 `docs/TECH_STACK.md` 第三节登记负责人与期限（没人认领等于没接入）。
2. 按 [技术栈适配](10-技术栈适配.md) 第三节的**最小规范四要素**写一份项目侧规范，不求一次写全。
3. 在 `stacks/registry.json` 登记为 `provisional`，把规范路径写进项目 `AGENTS.md` 的阅读顺序。
4. 一个月内转正，否则 `detect-stack --check` 会一直提示。

## 十四、模板规范里有一堆我的项目用不到的技术栈，要不要删

不删，**装箱**即可：不写进阅读顺序、不进 CI、不注入到项目侧文档，规范文件留在仓库里备用。

- 判断依据是你项目的实际技术栈，由 `node scripts/detect-stack.mjs` 探测，结果记在
  `workflow.config.json` 的 `stacks`（已启用）与 `availableStacks`（装箱）里。
- 团队换项目或加模块时直接启用，不用从零再写一遍——规范是团队资产，一份 Vue 3 规范可以同时喂给三个项目。
- 确实永久不会用到的，在项目 `AGENTS.md` 里写一句结论即可，不必物理删除。

详见 [技术栈适配](10-技术栈适配.md) 第四节。

## 十五、接入一个老项目，怎么保证不冲掉它已有的约定

模板的默认行为是**只补不改**：已存在的文件一律跳过。但有几类文件需要人工合并，`bootstrap` 会把它们列成融合清单：

| 已有的东西 | 合并方式 |
| --- | --- |
| 自有的 `CLAUDE.md` / `.cursorrules` | 内容并入 `AGENTS.md`，再跑 `node scripts/sync-agent-config.mjs` 重新生成 |
| 已有 CI（GitLab / Jenkins / 已有 workflows） | 在现有流水线里**追加**校验步骤，不要另建一套 |
| 已有钩子框架（husky / pre-commit / lefthook） | 二选一，两套并存必然互相绕过 |
| 已有 `package.json` 的 `validate` | 把三项检查合并进去，不要覆盖 |

同步脚本遇到没有生成标记的同名入口文件会跳过并提示，不会静默覆盖。完整规则见 [技术栈适配](10-技术栈适配.md) 第二节。

## 十六、接入后第一次校验报一堆错，怎么区分该修还是该豁免

老项目的存量问题分两类，处理方式完全不同：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| **必须修** | 密钥或口令入库、相对链接失效、模板必需文件缺失、共享文档链到仅模板仓库存在的路径（E307）、引用文件被 `.gitignore` 忽略（E308） | 立刻修。密钥类不支持豁免，门禁的价值就在这条底线 |
| **可登记豁免** | 历史文档是英文、`docs/` 根目录命名不符规范 | 登记到 `workflow.config.json` 的 `legacyDocs`，不阻塞门禁，随迭代迁移 |

`bootstrap` 会扫描项目已有的 Markdown，把命中「中文主语言」「docs 命名」两条规则的文件自动登记进 `legacyDocs`，
同一目录命中三篇以上折叠成 `目录/**`，避免清单过长：

```json
"trunkBranch": "master",
"legacyDocs": ["docs/deployment.md", "docs/superpowers/plans/**"]
```

三条使用规则：

1. 精确路径写全路径，整个目录写 `目录/**`；
2. 豁免只把这两类提示降级为警告，**密钥与断链照常报错**；
3. 迁移完一篇就删一条，删干净说明历史包袱清完了。

豁免清单不是免责声明：`docs/TECH_STACK.md` 的融合清单里会写明豁免了多少项，评审时能看到还剩多少没还。
新增文档不再享受豁免——只有登记在册的历史文件才降级。

## 十七、Git 钩子报「找不到 bash」怎么办

Windows 上如果装的是精简版 Git（MinGit、便携版），只有 `sh` 没有 `bash`：钩子脚本本身能跑，
但钩子里的 `npm run validate` 会因为 npm 找不到 shell 而失败，表现为
`/usr/bin/env: 'bash': No such file or directory`。

模板的钩子已经兼容这种情况：探测不到 `bash` 时自动降级为直接运行 node 脚本
（`check-docs`、`check-skills`、`detect-stack`），并打印一行提示说明降级原因。
在 PowerShell / CMD 里手动执行 `npm run validate` 不受影响，因为那里用的是 cmd.exe。

想彻底解决就装完整版 Git for Windows（自带 Git Bash），npm 脚本在钩子里即可正常工作。

## 十八、公司内网用 GitLab，模板里的 GitHub 文件怎么办

**平台产物有三套，只注入一套。** CI、`CODEOWNERS`、合并请求模板在各平台路径和语法完全不同，
`bootstrap` 会先探测项目实际托管在哪，再决定注入哪一套，不会让多个平台的配置文件同时躺在仓库里。
产物都放在 `templates/platform/<平台>/`，**目录内的相对路径就是注入后的位置**：

| 平台 | CI | 代码所有者 | 合并请求模板 |
| --- | --- | --- | --- |
| GitLab | `.gitlab-ci.yml` | 仓库根 `CODEOWNERS` | `.gitlab/merge_request_templates/Default.md` |
| GitHub | `.github/workflows/` | `.github/CODEOWNERS` | `.github/PULL_REQUEST_TEMPLATE.md` |
| Gitee | 不提供文件，在 Gitee Go 流水线页面配置 | 不支持 CODEOWNERS，用仓库设置的评审人 | `.gitee/PULL_REQUEST_TEMPLATE.md` |

探测规则：`--platform` 显式指定最优先；否则用「文件标记 + origin 地址」交叉判断，冲突时以 origin 为准
（仓库里另有其他平台的产物时会在输出里点名）；都没有时默认 GitLab。注入日志里有一行「托管平台：」，直接核对它。

四个容易困惑的点：

1. **GitLab / Gitee 项目里出现的 `.github/copilot-instructions.md` 不是平台产物**，而是 AI 工具入口：
   GitHub Copilot 插件只认这个固定路径，与代码托管在哪无关。不用 Copilot 就从 `workflow.config.json` 的
   `aiEntries` 里去掉 `copilot` 并重跑 `sync-agent-config.mjs`，`.github/` 目录就不会再出现；
   `CLAUDE.md`、`.cursor/rules/` 同理，用哪种工具就留哪个入口。
2. **项目已有 CI 时不会另建一套**：`bootstrap` 不覆盖 `.gitlab-ci.yml` / `.workflow/`，而是把它列进融合清单，
   要求你把校验命令**追加**进现有流水线，见 [接入清单](08-接入清单.md) 步骤 1。
3. **`--update` 不动平台产物**：CI 配置、`CODEOWNERS`、合并请求模板会被团队改，刷新模板时一律跳过，不会冲掉你的修改。
4. **本模板仓库根目录不带任何平台配置**：GitHub / GitLab / Gitee 三套产物只存在 `templates/platform/` 下，
   按项目实际托管平台注入。本仓库自己不需要根副本——`sync-platform.mjs` 只刷新根目录已存在的同名文件，
   将来若要恢复某一份（例如想让 Gitee 上的合并请求自带模板），从 `templates/platform/` 复制过来即可，门禁会接手后续一致性（E801）。

探测错了（例如仓库还没配远程、用的是自建 GitLab 域名但已在项目里放了 `.github/`），用 `--platform` 强制指定重跑即可；
真正长期不合的，建议按 [技术栈适配](10-技术栈适配.md) 的思路把仓库里那套用不到的产物删掉，只留实际使用的平台。

## 十九、模板仓库根目录有哪些目录是自己需要的

模板仓库**只保留自己真正在用的东西**，平台配置与 AI 入口都是「用哪个才生成哪个」：

| 路径 | 来源 | 不想要怎么办 |
| --- | --- | --- |
| `CLAUDE.md` | 由 `AGENTS.md` 生成（`aiEntries` 里有 `claude`） | 从 `workflow.config.json` 的 `aiEntries` 里去掉 `claude`，再跑 `sync-agent-config.mjs` |
| `.cursor/rules/00-workflow.mdc` | 同上，`cursor` 入口 | 去掉 `aiEntries` 里的 `cursor` 并重跑 |
| `.github/copilot-instructions.md` | 同上，`copilot` 入口（Copilot 插件只认这个固定路径，与托管平台无关） | 去掉 `aiEntries` 里的 `copilot` 并重跑 |
| 平台配置（`.github/workflows/`、`.gitlab-ci.yml`、`.gitee/` 等） | 只在 `templates/platform/` 下维护，按业务项目的托管平台注入 | 本仓库根本不会生成；要恢复包一层根副本，见上一节第 4 点 |

本仓库当前 `workflow.config.json` 里只启用了 `claude`，所以根目录只有 `CLAUDE.md` 一个生成物；
GitHub / GitLab / Gitee 三套平台产物都在 `templates/platform/`，不会因为本仓库托管在 Gitee 就给自己多放一份。
