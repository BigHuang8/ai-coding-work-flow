# 常见问题

## 一、流程太重怎么办

**先确认是不是真重。** 大多数「重」来自两种情况：

1. **该裁剪没裁剪。** 一行文案修改确实不需要写设计稿，见 [工作流总览](01-工作流总览.md) 的裁剪规则。
2. **文档写得过长。** `spec/` 页超过 200 行、验收报告超过 100 行，说明在写作文而不是在留证。留证要的是命令与输出，不是散文。

如果裁剪后依然觉得重，请提 RFC：说明哪一步实际没产生价值、建议怎么改。**不要私下跳过**，那会让门禁形同虚设。

## 二、需求一直在变，还要写 SPEC 吗

要写，但写的方式要变：

- 只固化**当前已确认**的部分，未确认的写进「待确认项」并写明谁来确认。
- 需求变更**直接改 `SPEC.md`**，并在 `MEMORY.md` 记一行变更原因。不要新建一堆平行文档。
- `spec/` 页保留**原始描述**不回改，这样事后能看出需求是怎么演进的。

## 三、AI 说「已完成」但其实是错的

这是最常见的失效模式。三个防御手段：

1. **要求 AI 先说要跑什么命令、预期看到什么**，再执行。预期错了当场就能发现理解偏了。
2. **要求原样贴回输出**。禁止「验证通过」这类无证据结论。
3. **失败时不立刻让 AI 改代码**，先让它解释失败原因与判断依据。直接改容易变成「打补丁掩盖问题」。

参见 [验收与证据留档](06-验收与证据留档.md) 第六节。

## 四、多人同时用 AI 改同一个模块，怎么不打架

1. **按文件划分**任务边界，见 [团队协作与角色](02-团队协作与角色.md) 第四节。
2. **接口先行**：先把签名与数据结构定下来提交，再并行实现。
3. **契约类文件单一写入者**：同一时间只允许一个人改 `docs/API_CONTRACT.md`。
4. 分支寿命不超过 3 个工作日，每天同步主干。

## 五、外部技能要不要拷进仓库

**不要拷贝正文。** 拷贝会产生两套各自漂移的副本。正确做法：

- 外部技能放 `.agents/skills/`，来源与哈希记在 `skills-lock.json`。
- 需要「改写以适配本项目」时，在 `skills/` 下写一个**自己的**技能，在其中引用外部技能并说明差异。
- 详见 [技能体系](03-技能体系.md)。

## 六、AI 读不到最新文档怎么办

上下文是「拉取式」的，AI 只会读你让它读的，或入口文件引用到的。所以：

1. 新文档必须**被 `AGENTS.md` 引用**，否则等于不存在。
2. 关键约束要写进 `AGENTS.md` 的硬性规则，而不是只躺在某个深层文档里。
3. 每次改完规范，顺手确认引用链没断——`node scripts/check-docs.mjs` 会检查链接有效性。

## 七、密钥不小心提交了怎么办

按 [安全与密钥](07-安全与密钥.md) 第五节执行。**第一件事是轮换密钥，不是删文件。** 历史提交仍在远程仓库里，删文件撤销不了泄漏。

## 八、评审者没时间评审

- 约定 24 小时响应 SLA，写进 `docs/02-团队协作与角色.md`。
- 超时由维护者指定替代评审者。
- 不允许「因为没人评审就直接合并」——那是把风险转移到线上。
- 一个人维护的项目：采用 30 分钟冷却期 + 自审清单填写记录。

## 九、模板里的文档和项目里已有的文档重复了

正常。接入时的处理原则：

| 情况 | 处理 |
| --- | --- |
| 项目已有自己的规范文档 | 让 `AGENTS.md` 指向它，不迁移、不改写 |
| 项目文档与本模板规范冲突 | 以项目实际为准，但在 `MEMORY.md` 记一行说明为何不一致 |
| 项目文档已过时 | 标记归档，不要直接删除，避免丢失历史决策 |

模板提供的是**方法与骨架**，不是必须逐字照搬的教条。

## 十、什么时候该改模板本身

出现以下信号时，说明模板需要演进：

- 某个门禁连续 3 个月没拦下过任何问题 → 考虑删除或简化
- 同一类问题在评审中反复出现 → 补一条规范或加一个自动检查
- 团队反复抱怨某一步 → 先做一次复盘，再改规则，不要凭感觉改

变更流程：提 RFC（现状 / 痛点 / 备选方案 / 影响面）→ 维护者裁定 → 改文档 + 改门禁 + 记 `CHANGELOG.md`。

## 十一、金额和时间到底该用什么字段类型

三条硬约定，不要临场发挥：

- **金额**用 `DECIMAL(18,2)`；需要更细粒度时用整数存「分」，并在字段注释里写明单位。禁止 `FLOAT` / `DOUBLE`——浮点会让对账长期对不平。
- **时间**用 `DATETIME(3)`，不用 `TIMESTAMP`（时区转换与 2038 问题）；全库统一，不要一半存时间戳一半存字符串。
- **前端传金额用字符串**：JavaScript 的数字是浮点，超过 15 位有效数字就会失真。

完整类型对照见 [数据库设计与建表规范](15-数据库设计与建表规范.md) 第五节。

## 十二、到底要不要建外键

- **默认不建物理外键**：并发写入、批量迁移、分库分表时外键都会成为障碍，一致性由应用层 + 唯一索引保证。
- **但唯一约束必须落库**（`uk_` 唯一索引）。业务唯一性靠应用层「先查再插」，在并发下必然被击穿——这不是风格问题，是正确性问题。
- 低频写入的配置类表可以建外键，但要在设计说明里写清理由与级联策略。

理由与替代方案见 [数据库设计与建表规范](15-数据库设计与建表规范.md) 第七节。
