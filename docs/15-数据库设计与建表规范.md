# 数据库设计与建表规范

本文件是表结构、索引与 SQL 的**唯一规范来源**，默认 MySQL 8.x + InnoDB + `utf8mb4`。其它数据库可替换语法，但命名、必备字段、变更流程三部分必须保留。

配套文档：[13-后端规范-Java-Spring](13-后端规范-Java-Spring.md)、[12-影响面与回归防护](12-影响面与回归防护.md)（改表结构属于公共改动）、[06-验收与证据留档](06-验收与证据留档.md)。

## 一、四条基本原则

1. **结构变更只通过迁移脚本**。任何手工执行的 DDL 都必须落成脚本文件，否则测试库与生产库必然不一致。
2. **一张表只表达一件事**。表名能用一句话说清，说不清就拆表。
3. **设计先于建表**。动笔前先写清楚：谁写入、谁读取、数据量级、保留期限、是否需要历史追溯。
4. **宁可加字段，不复用字段**。一个字段承担两种语义（例如 `status` 既表示订单状态又表示支付状态）是后期所有脏数据的源头。

## 二、命名约定

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 库 | `<项目>_<环境>`，环境后缀避免误连 | `hfzh_prod` |
| 表 | 小写下划线、**单数**、语义完整 | `order`、`order_item`、`customer_contact` |
| 关联字段 | `<单数表名>_id` | `order_id`、`customer_id` |
| 时间字段 | 统一 `_at` 后缀 | `created_at`、`updated_at`、`paid_at` |
| 状态字段 | 语义化命名，取值写进注释 | `status`、`audit_status` |
| 布尔字段 | `is_` 前缀或过去分词 | `is_default`、`enabled`、`deleted` |
| 唯一索引 | `uk_<表>_<字段>` | `uk_order_order_no` |
| 普通索引 | `idx_<表>_<字段>` | `idx_order_customer_id` |
| 金额字段 | 后缀标明币种或用途 | `amount`、`premium_amount` |

禁止：中文表名、拼音缩写（团队约定的例外需写进本文件）、保留字（`order` 这类与 SQL 关键字冲突时统一加业务前缀，如 `biz_order`）、无意义后缀（`_data`、`_info`、`_tmp` 留在正式表里）。

## 三、必备字段

每张业务表都必须包含以下字段（日志表、流水表可省略 `updated_*` 与 `version`，但要在设计说明里写明理由）：

```sql
id          BIGINT       NOT NULL COMMENT '主键（雪花 ID）',
created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
updated_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
created_by  BIGINT       NOT NULL DEFAULT 0 COMMENT '创建人 ID，0 表示系统',
updated_by  BIGINT       NOT NULL DEFAULT 0 COMMENT '更新人 ID，0 表示系统',
deleted     TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '逻辑删除：0 正常 1 已删除',
version     INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
```

- 审计字段不是可选项：出问题时「谁改的、什么时候改的」只能靠它们回答。
- 业务代码禁止覆盖 `created_at` / `created_by`。
- 逻辑删除后需要唯一性时，用 `deleted` 参与唯一索引，或把 `order_no` 加上删除时间后缀，避免「删了就不能再建同名」。

## 四、主键与 ID 策略

- 统一 `BIGINT` 雪花 ID：分布式下不冲突、整体递增、不暴露业务量级。
- **禁止**用业务字段（手机号、身份证、编号字符串）做主键。
- 自增 ID 只用于内部字典表，且不得作为对外接口暴露的 ID。
- 需要 UUID 时用 `BINARY(16)` 存储，禁止用 `VARCHAR(36)`（索引体积翻倍且随机写入放大）。
- 对外编号（订单号、保单号）单独设字段 + 唯一索引，与主键解耦。

## 五、字段类型与精度

| 用途 | 类型 | 说明 |
| --- | --- | --- |
| 金额 | `DECIMAL(18,2)` | **禁止 `FLOAT` / `DOUBLE`**，浮点会带来对账差错 |
| 金额（分为单位） | `BIGINT` | 需在注释与文档中写明单位为分 |
| 数量 / 次数 | `INT` | 不用 `VARCHAR` 存数字 |
| 比例 / 费率 | `DECIMAL(9,4)` | 明确是百分数还是小数 |
| 时间 | `DATETIME(3)` | 不用 `TIMESTAMP`（时区与 2038 问题），需精确到秒时用 `DATETIME` |
| 布尔 | `TINYINT(1)` | 与 Java `Boolean` 映射 |
| 短文本 | `VARCHAR(n)` | 设合理上限（姓名 64、手机号 20、单号 64、标题 255） |
| 长文本 | `TEXT` / `LONGTEXT` | 放独立扩展表，避免影响主表行读取 |
| JSON | `JSON` | 只放「不需要按内部字段检索」的结构 |
| 枚举 | `TINYINT` + 注释，或码表 | 禁止用中文字符串做业务判断 |
| 二进制 | `BLOB` 禁止入库 | 文件放对象存储，库里只存 URL 与元信息 |

约定：**任何需要被查询、排序、统计的字段都不能藏在 JSON 里**，必须拆成独立列并建索引。

## 六、索引规范

- 主键即聚簇索引，保持短小；不要在宽表上放大主键。
- 业务唯一性**必须落库**（`uk_` 唯一索引）：应用层「先查再插」在并发下必然被击穿。
- 联合索引顺序：等值条件在前、范围条件在后，遵循最左前缀。
- 单表索引数量 ≤ 5 个（含主键），每加一个索引都要说明它服务哪条查询。
- 低区分度字段（性别、状态、逻辑删除）不单独建索引，需与其它列组成联合索引。
- **禁止在索引列上做运算或隐式转换**：

```sql
-- 反例：索引失效
SELECT * FROM order WHERE DATE(created_at) = '2026-09-24';
SELECT * FROM customer WHERE phone = 1380000000;

-- 正例：范围查询，且类型与列定义一致（phone 为 VARCHAR）
SELECT * FROM order WHERE created_at >= '2026-09-24 00:00:00' AND created_at < '2026-09-25 00:00:00';
SELECT * FROM customer WHERE phone = '1380000000';
```

- 高频只读查询可用覆盖索引减少回表；长字符串（URL、备注）用前缀索引。
- 新增索引前先看现有索引，避免功能重复的冗余索引。

## 七、约束、默认值与字符集

- 字段尽量 `NOT NULL` + 默认值：`NULL` 与 `0`、空字符串语义不同，越少歧义越好。
- 全库统一 `utf8mb4` 与统一排序规则，禁止表间混用（JOIN 时会导致索引失效）。
- **每张表、每个字段都必须有 `COMMENT`**：注释是生成文档与排障的依据。
- 外键：默认**不建物理外键**，由应用层与唯一索引保证一致性；确有强一致要求时再建，并在设计说明中写清理由与级联策略。
- 禁止用触发器改业务数据（难以排查、迁移困难）；仅强约束场景可使用并登记到设计文档。
- 默认值不要用业务相关的时间常量（例如 `'2000-01-01'` 冒充空值），用 `NULL` 或 `0` 并写明语义。

## 八、表设计模式

| 场景 | 做法 |
| --- | --- |
| 主数据 + 明细 | 主表 `order` + 明细表 `order_item`，明细用 `order_id` 关联 |
| 当前状态 + 变更历史 | 主表存当前状态，变更流水单独一张表（只增不改） |
| 字典 / 码表 | 值与文案分离，前端展示走字典接口，不在业务表里存中文 |
| 日志 / 审计 | 只增不改，按月分表或定期归档，不与业务表混用 |
| 大字段 | 拆到扩展表（`order_ext`），主表保持窄 |
| 冗余字段 | 允许为查询性能冗余，但必须写明「谁维护、何时更新」 |
| 多租户 / 多机构 | 统一 `tenant_id` 或 `org_id` 放在最左等值位置并进索引 |

## 九、DDL 变更流程

目录约定（随模板注入到业务项目根目录，说明见 `db/README.md`，可复制模板见 `db/建表模板.sql`）：

```text
db
├── migration
│   └── V202609241530__order_add_pay_channel.sql
└── 建表模板.sql
```

规则：

1. **脚本只增不改**：已执行过的脚本禁止修改，改错就新增一个修正脚本。
2. 命名 `V<YYYYMMDDHHmm>__<英文短描述>.sql`，一个脚本只做一件事（加字段、加索引分开）。
3. 脚本头部用注释写清：目的、影响表、预估耗时、回滚方式、关联需求。
4. 流程：本地库验证 → 测试库执行 → 预发验证 → 生产窗口执行 → 校验数据 → 记录到变更单与 `docs/verification/`。
5. **禁止**：直连生产改表、在业务代码里 `CREATE TABLE`、先手工改再补脚本。

大表变更（数据量超千万行）额外动作：

- 加字段：放在表末尾（MySQL 8 支持 instant add column），避免中间插入导致重建表。
- 加索引：低峰执行，优先 `ALGORITHM=INPLACE, LOCK=NONE`，超时时间预留足够。
- 删字段 / 改名：分三步走——加新字段 → 双写并回填 → 确认无引用后删旧字段，禁止一步到位。
- 改类型 / 字符集：评估重建表的时间与磁盘空间，必要时用在线工具。

## 十、SQL 编写规范

- 禁止 `SELECT *`，按需列出字段。
- `UPDATE` / `DELETE` 必须带 `WHERE`；执行前先用同条件 `SELECT` 确认影响行数。
- 批量插入每批不超过 500 行；批量更新用 `CASE WHEN` 或临时表，避免上万次单条更新。
- 避免超大 `IN` 列表（超过 1000 个值），改用 JOIN 或临时表。
- 深分页用游标（`WHERE id > ? ORDER BY id LIMIT ?`）或延迟关联，禁止 `LIMIT 100000, 20`。
- 禁止 `ORDER BY RAND()`；随机抽样在应用层做或预生成。
- 事务尽量短：不在事务里做远程调用、文件 IO、大批量循环。
- 统计与分析类查询走从库或数仓，不与在线业务抢资源。

## 十一、数据安全与合规

- 生产数据不得导出到个人环境；确需排查时导出脱敏样本。
- 敏感字段（身份证、银行卡、健康信息）加密存储，并在设计文档登记加密方式与密钥管理位置。
- 敏感字段禁止进索引明文（需要检索时存哈希列）。
- 删除优先逻辑删除 + 归档；物理删除仅用于合规要求，并保留审计记录。
- 备份与恢复演练至少每季度一次，恢复流程写入 `docs/06-验收与证据留档.md` 对应的证据目录。

## 十二、建表 / 改表评审清单

- [ ] 表名、字段名符合命名约定，注释齐全（表注释 + 字段注释）
- [ ] 必备字段（审计、逻辑删除、版本号）齐全，例外已写明理由
- [ ] 主键类型与 ID 生成策略符合第四节
- [ ] 金额用 `DECIMAL`，时间用 `DATETIME(3)`，无 `FLOAT` / `TIMESTAMP`
- [ ] 业务唯一性有 `uk_` 唯一索引
- [ ] 每个新增索引都能说出它服务的具体查询，且总数 ≤ 5
- [ ] 变更脚本已按第九节命名与注释，含回滚方式
- [ ] 大表变更已评估锁表时间与执行窗口
- [ ] 影响面已按 `12-影响面与回归防护.md` 反查（哪些代码、哪些接口、哪些报表）
