# 技能体系

技能（Skill）是把「团队怎么做事」变成 AI 可复用能力的最小单元。本文定义技能的分层、写法、引入、自研、升级与退役。

## 一、三层技能

| 层 | 位置 | 来源 | 语言 | 变更方式 |
| --- | --- | --- | --- | --- |
| 自研技能 | `skills/<name>/SKILL.md` | 团队自己写 | 中文 | 走技能共建流程 |
| 引入技能 | `.agents/skills/<name>/SKILL.md` | 外部仓库 | 原语言 | 锁定哈希，按需升级 |
| 项目专属技能 | 业务项目内 `skills/` | 接入后本地沉淀 | 中文 | 项目内评审 |

**关键规则：不要把外部技能复制进 `skills/`。** 复制会产生两套各自漂移的副本，这是本模板明确要避免的问题。外部技能一律放 `.agents/skills/`，用 `skills-lock.json` 管版本。

## 二、SKILL.md 的结构规范

```markdown
---
name: skill-name
description: 一句话说明什么时候用它（写清触发场景，不写实现细节）
argument-hint: "[参数说明]"
---

# 技能标题

## 何时使用
## 何时不要使用
## 输入
## 步骤
## 输出
## 质量门禁
## 反模式
```

必填字段只有两个：`name`（小写连字符）与 `description`。`description` 决定 AI 能否在正确时机想起它，请写「什么场景下用」，不要写「本技能会做 X」。

## 三、自研技能的编写原则

1. **全中文正文**，代码、命令、路径保持原文。
2. **可验证的输出**：必须定义清楚「产出什么、怎么判定合格」，不能只写流程描述。
3. **不写业务数据**：技能是通用能力，具体业务信息应放在 `SPEC.md` 或 `spec/` 中。
4. **不写任何密钥**：包括示例里的「真实但已废弃」口令。
5. **不重复制度层内容**：需要引用规范时写路径，例如「按 `docs/05-分支提交与评审.md` 的提交格式」，不要复制一份。
6. **保持单一职责**：一个技能只解决一类问题，步骤超过 20 条时应拆分。

## 四、技能共建流程

```text
提案 → 试点 → 评审 → 发布 → 复盘
```

| 阶段 | 要求 | 产出 |
| --- | --- | --- |
| 提案 | 说明要解决什么重复劳动、当前怎么做、预计节省多少 | issue 或 `spec/` 页 |
| 试点 | 由提案者在真实任务里用至少 2 次 | 两次使用的实际输入输出 |
| 评审 | 检查是否符合第三节的六条原则，是否与既有技能重复 | 评审结论 |
| 发布 | 合并并更新 `skills/README.md` 与 `CHANGELOG.md` | 技能文件 |
| 复盘 | 使用满 1 个月后确认是否继续保留 | 保留 / 改造 / 退役结论 |

**判定标准：** 如果你在两次不同任务里重复向 AI 解释了同一套步骤，就该把它写成技能。

## 五、技能来源准入：只允许仓库内技能

**硬规则：开发本项目只能使用仓库内技能。** 白名单只有两个位置：

| 位置 | 类型 | 准入条件 |
| --- | --- | --- |
| `skills/<name>/SKILL.md` | 自研 | 走第四节共建流程，并登记在 `skills/README.md` 的清单里 |
| `.agents/skills/<name>/SKILL.md` | 引入 | 来源与哈希登记在 `skills-lock.json` |

**禁止的来源**：

- 个人全局技能目录（`~/.codex/skills`、`~/.claude/skills`、个人 Cursor 规则等）——换个人、换台机器就不存在；
- 临时安装、来源不明的技能包，包括从聊天记录里粘贴过来的技能正文；
- 直接安装到全局或其他仓库，然后拿「我本地有这个技能」当作交付依据；
- 把外部技能正文拷进 `skills/`（会产生两套各自漂移的副本，见第一节）。

**为什么定这么严**：

1. **可复现**：换个人、换台机器、在 CI 里跑，行为必须一致。个人技能做不到这一点。
2. **可评审**：技能是团队资产，它决定 AI 怎么改代码，影响力不比业务源码小，必须走 PR。
3. **可追溯**：`skills-lock.json` 记录来源与哈希，升级与退役都是一次可回滚的提交。
4. **安全**：个人技能目录里常混有私有约定、内网地址甚至明文口令，一旦被引用就是泄漏面。

**唯一例外**：个人技能可以用于「探索、学习、一次性试验」，但**不得作为交付依据**。如果某个个人技能要在项目里长期使用，先按第六节完成引入，落到 `.agents/skills/` 后再在任务中使用。

**这条规则怎么被拦住**：

```bash
node scripts/check-skills.mjs   # 已接入 npm run validate、.githooks/pre-commit 与 CI
```

| 规则 | 检查内容 |
| --- | --- |
| E601 | 技能目录名必须是小写连字符形式 |
| E602 | 技能目录必须有 `SKILL.md` |
| E603 | `SKILL.md` 必须有 front-matter 的 `name` / `description`，且 `name` 与目录名一致 |
| E604 | 技能只能出现在 `skills/` 与 `.agents/skills/`，白名单之外的 `SKILL.md` 一律报错 |
| E605 | 技能内容不得引用仓库外的个人目录或绝对路径 |
| E606 | `skills/README.md` 技能清单与目录必须一致 |

## 六、引入外部技能

### 评估清单

- [ ] 解决的是我们真实遇到的问题吗（不是「看起来很强」）
- [ ] 与已有自研技能是否重叠？重叠时以谁为准
- [ ] 是否有 LICENSE，是否允许当前使用场景
- [ ] 是否要求访问网络、上传代码或数据
- [ ] 是否会写入仓库外的路径
- [ ] 是否有明确的输入输出与失败处理

### 引入步骤

```bash
# 1. 安装到项目内（不要用全局 -g，全局安装不受版本锁定保护）
npx skills add <owner>/<repo>@<skill> -y

# 2. 登记来源与哈希
node scripts/sync-agent-config.mjs --lock

# 3. 验证：在一个真实任务里用一次，确认行为符合预期
```

### 升级与退役

- **升级**：单独提交，说明变更点与影响面；升级后必须实际用一次再合并。
- **退役**：从 `skills-lock.json` 移除，并在 `CHANGELOG.md` 记录原因与替代方案。

## 七、当前技能清单

| 技能 | 类型 | 用途 |
| --- | --- | --- |
| `flow-orchestrator` | 自研 | 判断当前处于六阶段哪一步，给出下一步动作 |
| `impact-analysis` | 自研 | 反查调用方、记录基线、做回归验证 |
| `requirement-intake` | 自研 | 接收 PRD / 原型，归档原件并逐条标注技术实现 |
| `spec-writer` | 自研 | 把口头需求变成可验收的需求条目与 `spec/` 留档 |
| `dual-axis-review` | 自研 | 规范轴 + 需求轴的双轴评审 |
| `evidence-driven-verification` | 自研 | 生成可复现的验收证据 |

## 八、反模式

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 把项目业务规则写进通用技能 | 技能无法复用到其他项目 | 通用能力进技能，业务规则进 `SPEC.md` |
| 用个人目录里的技能干活 | 同事和 CI 无法复现，换台机器就失效 | 引入到 `.agents/skills/` 并登记哈希后再用 |
| 技能正文从聊天里粘贴进仓库 | 来源与版本不可追溯 | 走第六节引入流程 |
| 技能里写死服务器地址或口令 | 泄漏风险 + 环境耦合 | 用环境变量，写进 `.env.example` 占位 |
| 为每个小步骤建一个技能 | 技能爆炸，AI 选择困难 | 按「一类问题」建技能 |
| 引入技能后不登记哈希 | 版本漂移不可控 | 一律登记进 `skills-lock.json` |
| 技能改完不验证 | 下次用才发现坏了 | 真实任务里跑一次再合并 |
