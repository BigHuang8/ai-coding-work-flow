# 接入清单

把一个真实项目接进本工作流，按本文从上到下执行。全程约 1-2 小时，建议由一名维护者主导。

> 六步流程图见 [`assets/onboarding.png`](../assets/onboarding.png)：体检 → 预览 → 注入 → 融合清单 → 认领缺口 → 验收。

## 一、前置条件

- [ ] 项目已有可运行的构建与测试命令（没有的话先补齐，工作流依赖它做门禁）
- [ ] 项目使用 Git，且有远程仓库
- [ ] 团队已就「采用本工作流」达成一致（至少包含一名愿意当评审者的人）

## 二、步骤

### 步骤 0：接入体检

先摸清项目现状，再决定改什么。**已有约定一律不覆盖**，只补缺的——冲掉项目既有约定比不接入更糟。

```bash
# 看项目实际用了哪些技术栈、哪些模板有规范、哪些是缺口
node scripts/detect-stack.mjs --target ../your-project
```

输出分三类，处理方式见 [技术栈适配](10-技术栈适配.md)：

| 分类 | 含义 | 处理 |
| --- | --- | --- |
| 已启用 | 项目用到、模板有规范 | 规范进阅读顺序，校验命令进 `validate` |
| 装箱未启用 | 模板有规范、项目没用到 | 不注入、不进阅读顺序、不进 CI |
| 缺口 | 项目用到、模板没规范 | 认领后写最小规范，先登记 `provisional` |

缺口应在接入当天就指派负责人与期限，写进 `docs/TECH_STACK.md`。没人认领的缺口等于这个项目没接入。

### 步骤 1：注入模板文件

```bash
# 先预览
node scripts/bootstrap.mjs --target ../your-project --dry-run

# 确认后执行
node scripts/bootstrap.mjs --target ../your-project

# 技术栈默认自动探测；需要人工纠正时显式指定
node scripts/bootstrap.mjs --target ../your-project --stack java-springboot,vue3
```

默认行为：**已存在的文件不覆盖**，避免冲掉项目现有文档。需要强制覆盖时加 `--force`，并先确认备份。

**平台产物按托管平台三选一**：CI 配置、`CODEOWNERS`、合并请求模板各平台路径与语法都不同，`bootstrap` 只注入一套。
产物都放在模板仓库的 `templates/platform/<平台>/` 下（该目录不注入业务项目，只在模板仓库里维护），
**目录内的相对路径就是注入到本项目后的位置**：

| 探测到的平台 | 注入的文件 |
| --- | --- |
| GitLab | `.gitlab-ci.yml`、`CODEOWNERS`、`.gitlab/merge_request_templates/Default.md` |
| GitHub | `.github/workflows/`、`.github/CODEOWNERS`、`.github/PULL_REQUEST_TEMPLATE.md` |
| Gitee | `.gitee/PULL_REQUEST_TEMPLATE.md`（Gitee Go 流水线在网页端配置，见步骤 7） |

探测规则，按顺序判定：

1. `--platform` 显式指定，最高优先级；
2. 文件标记 + `origin` 地址交叉判断：`.gitlab-ci.yml` / `.gitlab/` 指向 GitLab，`.gitee/` / `.workflow/` 指向 Gitee，`.github/workflows/` 指向 GitHub；
3. 两者冲突时**以 origin 为准**（远程地址才代表项目真正的归属），并在输出里提示仓库里另有哪套产物；
4. 只有文件标记没有远程时，按 GitLab → Gitee → GitHub 取第一个；
5. 都识别不出时**默认 GitLab**（企业内网最常见）。

输出里有一行「托管平台：」，核对它即可。不对就手动纠正后重跑（平台文件在 `--update` 时不会被覆盖，不会冲掉你已改的内容）：

```bash
node scripts/bootstrap.mjs --target ../your-project --platform gitlab
node scripts/bootstrap.mjs --target ../your-project --platform github
node scripts/bootstrap.mjs --target ../your-project --platform gitee
```

平台目录里只会出现你真正需要的东西：Gitee 项目不会多出 `.github/workflows/`，GitLab 项目不会多出 `.gitee/`。
唯一例外是 `.github/copilot-instructions.md`（AI 工具入口，不是平台产物）：GitHub Copilot 插件只认这个固定路径，
项目托管在 GitLab / Gitee 也会生成，**不用 Copilot 的话按步骤 5 从 `aiEntries` 里去掉**，`.github/` 目录就不会出现。

注入时会自动识别主干分支并写入 `workflow.config.json`。**如果项目真正的主干不是 `main` / `master`（例如是 `int` / `develop`），立刻改掉**，否则任务占用看板会拿错基线：

```bash
node scripts/bootstrap.mjs --target ../your-project --trunk int
# 或直接编辑 workflow.config.json 的 "trunkBranch"
```

同时生成这些内容：

- `docs/TECH_STACK.md`：已启用栈、装箱栈、缺口与融合清单都在里面；
- 项目侧 `package.json`：没有就生成一份只含校验脚本的；已有则另存为 `.package.json.workflow`，把 `scripts` 合并进现有文件后删除；
- `assets/`：README 与文档引用的流程配图，漏注入会让文档里的图片链接变成断链；
- `workflow.config.json` 的 `legacyDocs`：项目历史文档中不符合「中文主语言」「docs 命名」的自动登记为接入豁免，不阻塞门禁，随迭代迁移（见 [常见问题](09-常见问题.md) 第十六节）。

**融合清单必须逐项处理**：项目已有的 AI 入口（`CLAUDE.md` 等）、CI、钩子框架、`validate` 命令都不会被覆盖，需要人工合并。规则见 [技术栈适配](10-技术栈适配.md) 第二节。其中「文档基线」一项是豁免登记，不要求立刻迁移。

### 步骤 2：定制 AGENTS.md

依次修改：

- [ ] 第一节「沟通与文档原则」：补充公司或团队特有的沟通约定
- [ ] 第二节「阅读顺序」：把技术栈规范指向真实存在的文件
- [ ] 第六节「命令索引」：换成项目真实的校验命令
- [ ] 第八节「提交规范」：确认 `scope` 取值与项目的模块划分一致

**不要**在 `AGENTS.md` 里堆砌业务细节，那是 `SPEC.md` 的职责。

### 步骤 3：配置 CODEOWNERS

编辑 CODEOWNERS（GitHub 在 `.github/CODEOWNERS`，GitLab 在仓库根 `CODEOWNERS`），把 `@your-team/...` 换成真实团队或人员。
Gitee 不支持 CODEOWNERS，改为在仓库设置里指定评审人；规则本身（哪类文件谁评审）仍按 [团队协作与角色](02-团队协作与角色.md) 写进 `docs/` 备查：

```text
*                       @your-team/maintainers
/AGENTS.md              @your-team/maintainers
/docs/                  @your-team/maintainers
/skills/                @your-team/maintainers
/scripts/               @your-team/maintainers
```

### 步骤 4：接入校验命令

在项目根 `package.json` 增加统一入口，让钩子与 CI 只认一个命令：

```json
{
  "scripts": {
    "validate": "npm run validate:docs && npm run validate:skills && npm run validate:stacks && npm run validate:standards && npm run typecheck",
    "validate:docs": "node scripts/check-docs.mjs",
    "validate:skills": "node scripts/check-skills.mjs",
    "validate:stacks": "node scripts/detect-stack.mjs --check",
    "validate:agents": "node scripts/sync-agent-config.mjs --check",
    "validate:platform": "node scripts/sync-platform.mjs --check"
  }
}
```

技能检查是接入后的必选项：**开发本项目只使用仓库内技能**——自研放 `skills/`，引入放 `.agents/skills/` 并登记 `skills-lock.json`；个人目录下的技能（`~/.codex/skills`、`~/.claude/skills` 等）不得作为交付依据。规则见 [技能体系](03-技能体系.md) 第五节。

技术栈检查同样必选：它保证「项目用到的栈都有规范在场」，缺口会被点名。接入期用默认的警告模式，
稳定后改成 `node scripts/detect-stack.mjs --check --strict`，让缺口直接拦住合并，见 [技术栈适配](10-技术栈适配.md) 第五节。

### 步骤 5：生成各 AI 工具入口

```bash
node scripts/sync-agent-config.mjs
```

该命令以 `AGENTS.md` 为唯一事实来源，按 `workflow.config.json` 的 `aiEntries` 生成入口文件，
默认三个都生成：`CLAUDE.md`（claude）、`.cursor/rules/00-workflow.mdc`（cursor）、`.github/copilot-instructions.md`（copilot）。

团队不用的工具就去掉对应项，脚本不再生成，项目里也不会留下用不到的目录——比如不用 Copilot 就没有 `.github/`：

```json
"aiEntries": ["claude", "cursor"]
```

改完重跑 `node scripts/sync-agent-config.mjs`；已经生成过的停用入口会提示删除，不会悄悄留在仓库里。

**不要手工编辑这些入口文件**，它们会被覆盖；要改规范请改 `AGENTS.md` 或 `docs/`。

### 步骤 6：安装 Git 钩子

```bash
bash scripts/install-hooks.sh
# 或
pwsh scripts/install-hooks.ps1
```

装完立刻验证：

```bash
# 应当被拒绝
git commit --allow-empty -m "随便写点什么"

# 应当通过
git commit --allow-empty -m "chore(workflow): 验证提交信息钩子"
```

### 步骤 7：配置远程约束

在代码托管平台（Gitee / GitHub / GitLab）完成：

- [ ] 保护主干：禁止直接推送，必须走合并请求（GitHub 叫 PR，GitLab 叫 MR）
- [ ] 要求至少 1 名评审通过
- [ ] 要求 CI 通过才能合并
- [ ] 启用合并请求模板（GitHub 读 `.github/PULL_REQUEST_TEMPLATE.md`，GitLab 读 `.gitlab/merge_request_templates/Default.md`，Gitee 读 `.gitee/PULL_REQUEST_TEMPLATE.md`）
- [ ] CI 里跑同一套校验命令：GitLab 用注入的 `.gitlab-ci.yml`；Gitee Go 在仓库的「流水线」页面新建流水线，把 `node scripts/check-docs.mjs`、`node scripts/check-skills.mjs`、`node scripts/detect-stack.mjs --check`、`node scripts/sync-agent-config.mjs --check`、`node scripts/sync-platform.mjs --check` 依次加为构建步骤

### 步骤 8：试运行一次完整流程

挑一个**小且真实**的需求（半天内能完成），完整走完六阶段：

1. `node scripts/new-spec.mjs --title "..." --with-artifacts --with-verification` 建档
2. 与 AI 一起补成可验收的 `SPEC.md` 条目
3. 写设计与计划（可精简）
4. TDD 实现
5. 证据留档到 `docs/verification/`
6. 走一次 PR 与双轴评审
7. 合并并写 PR 回滚说明

试运行的目的不是交付价值，而是**暴露流程里不顺手的地方**。跑完开 30 分钟复盘，把卡点改掉。

### 步骤 9：宣布与培训

- [ ] 在团队群公告：从某日起新需求一律走本流程
- [ ] 安排一次 30 分钟演示：现场走一遍 ① 和 ④（需求澄清与证据留档最容易被跳过）
- [ ] 指定维护者与评审者名单，写进 `docs/02-团队协作与角色.md`

### 步骤 10：模板迭代后的同步

模板会持续演进（修 bug、补规则、加配图）。项目接入后不必重新注入，用 `--update` 刷新托管文件：

```bash
node scripts/bootstrap.mjs --target ../your-project --update --dry-run   # 先看会更新什么
node scripts/bootstrap.mjs --target ../your-project --update
```

`--update` 的边界：

| 文件 | 行为 |
| --- | --- |
| 模板托管（`docs/`、`skills/`、`scripts/`、`stacks/`、`.githooks/`、`assets/` 等） | 刷新到模板最新版 |
| 平台相关文件（CI 配置、`CODEOWNERS`、合并请求模板） | 不动：这些几乎必然被团队改过，覆盖会丢内容 |
| `AGENTS.md`、`SPEC.md`、`MEMORY.md` | 已把占位符替换成项目内容时保留项目版本；仍是模板原样时才刷新 |
| `.gitignore`、`.gitattributes`、`.env.example`、`package.json`、`docs/TECH_STACK.md` | 一律不动，避免冲掉你的合并结果与登记 |
| 项目自己的文件（`README.md`、`docs/deployment.md` 等） | 不在托管范围内，不受影响 |

更新后重跑 `npm run validate` 确认没有回归再提交。技术栈探测结果变了时，
`--update` 会提示 `docs/TECH_STACK.md` 与探测结果不一致，按提示手动更新，或用 `--force` 重新生成
（注意缺口表的负责人与期限需要重填）。

## 三、完成标志

全部满足才算接入完成：

- [ ] `node scripts/check-docs.mjs` 通过
- [ ] `node scripts/sync-agent-config.mjs --check` 通过
- [ ] `node scripts/detect-stack.mjs --check` 通过，缺口在严格模式下会被拦住
- [ ] `docs/TECH_STACK.md` 的三类清单与实际一致，缺口有负责人与期限
- [ ] 融合清单（已有的 AI 入口 / CI / 钩子 / validate）逐项处理完毕
- [ ] CI 与合并请求模板和项目实际托管平台一致（用 GitLab 就不该留着 `.github/workflows/`，反之亦然）
- [ ] `bash scripts/install-hooks.sh` 执行后，非法提交信息会被拒绝
- [ ] `main` 分支已开启保护，无法直接推送
- [ ] 已有至少 1 个 PR 走完了完整的六阶段
- [ ] `docs/verification/` 下至少有 1 份可被他人复现的证据
- [ ] 团队里每个人都至少提交过一次合规的 PR

## 四、常见坑

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 直接覆盖已有文档 | 丢失项目历史决策 | 先 `--dry-run`，只用默认的非覆盖模式 |
| 把业务规则抄进 `AGENTS.md` | 入口臃肿、两处漂移 | 只保留索引，业务规则放 `SPEC.md` |
| 校验命令形同虚设（永远通过） | 门禁失效，等于没有 | 故意制造一次失败，确认能被拦住 |
| 项目托管在 GitLab，却注入了 `.github/` 那套 CI 与模板 | 流水线根本不跑，评审模板也看不到 | 核对 `bootstrap` 输出的「托管平台」一行，不对就 `--platform gitlab` 重跑 |
| 在项目里手工改了 CI / 合并请求模板，指望模板仓库下次同步会带上 | 模板不知道你的改动，也不会覆盖它；通用规则沉不下来，每个项目各写一份 | 团队级规则要回灌到模板仓库的 `templates/platform/`，再按接入清单的 `--update` 分发给各项目 |
| 只有一个人懂流程 | 人员变动后流程崩塌 | 至少两人能独立完成评审 |
| 一次性全量推行 | 团队抵触，阳奉阴违 | 先用一个小需求试点，再逐步扩大 |
| 把旧项目的口令写进 `.env.example` | 泄漏 | 只写占位符 |
| 直接覆盖项目自有的 `CLAUDE.md` / CI / 钩子 | 原有约定失效，团队失去信任 | 先体检，按融合清单逐项合并 |
| 把本项目用不到的栈规范也写进阅读顺序 | AI 每次多读无关文档，规范之间互相干扰 | 只列已启用栈，其余装箱 |
| 缺口长期不认领，AI 自由发挥 | 同一技术栈两套写法，返工 | 接入当天指派负责人与期限，`--strict` 拦住 |
