# 验收与证据留档

「我觉得没问题」不是结论，「命令 + 原始输出 + 复现步骤」才是。本文定义证据的形态与留档规范。

> 配图见 [`assets/evidence.png`](../assets/evidence.png)：三条标准、留档位置、证据类型、基线对比与未覆盖项。

## 一、什么算证据

证据必须同时满足三条：

| 要素 | 含义 | 反例 |
| --- | --- | --- |
| 可复现 | 换一个人按文档操作，得到同样结果 | 「我本地是好的」 |
| 原始 | 保留命令与真实输出，未加工 | 「测试都通过了」 |
| 可定位 | 标明版本、环境、数据前提 | 只贴一张没有上下文的截图 |

## 二、目录与命名

```text
docs/verification/<YYYYMMDD>-<主题>/
├── 验收报告.md            # 结论与逐条对照
├── 命令记录.md            # 实际执行的命令与原始输出
├── assets/                # 截图、录屏、导出文件
└── （可选）report.json     # 机器可读的测试报告
```

主题命名与 `spec/` 保持一致，例如 `20260924-客户列表团队筛选`。一个需求一个目录，不要复用。

涉及界面时，`assets/` 下应包含**原型 vs 实际**的对比图，命名用 `<页面名>-comparison.png`，与 `spec/<主题>/原型/` 下的原型件同名，便于评审时左右对照。逐条验收表的编号请沿用 `spec/<主题>/需求与技术对照.md` 中的 `R1`、`R2`。

## 三、证据类型矩阵

按变更类型选择**至少两类**证据：

| 变更类型 | 推荐证据 |
| --- | --- |
| 接口 / 服务端逻辑 | 单元测试输出、接口契约测试输出、curl 请求与响应原文 |
| 页面 / 交互 | 关键状态截图（默认、加载、空态、异常）、多分辨率截图 |
| 数据 / 迁移 | 迁移前后行数对比、抽样数据对比、回滚演练记录 |
| 性能优化 | 优化前后同一场景的耗时或资源占用数据 |
| 配置 / 部署 | 启动日志关键行、健康检查响应、回滚步骤演练记录 |
| 改动既有代码 | 回归验证结果，并与改动前基线对比（区分新增失败与既有失败） |
| 纯文档 | 渲染结果截图或预览链接（涉及链接有效性时必须验证） |

## 五、命令记录模板

````markdown
# 命令记录

## 用例 2：不选团队等于全部

```bash
curl -s ".../api/customers?page=1&pageSize=20" -H "Authorization: Bearer ***"
```

输出（节选）：

```json
{"code":0,"data":{"total":37,"list":[]}}
```

结论：total=37，与全量一致。
````

规则：**命令与输出一起粘贴**，不要只贴输出；敏感信息用 `***` 脱敏，不要贴真实 Token。

## 六、AI 参与验证时的要求

1. 让 AI 先给出「打算跑哪些命令、预期看到什么」，再执行。
2. 执行结果必须原样贴回，包括失败；**禁止让 AI 只汇报「验证通过」**。
3. 命令失败时，不要立刻让 AI 改代码；先让它解释失败原因与判断依据。
4. 涉及环境的验证要写清环境，本地通过不等于测试环境通过。

## 七、反模式

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 只写「已完成，测试通过」 | 不可复现，评审无法核对 | 附命令与原始输出 |
| 截图没有前提数据 | 别人无法判断是否覆盖了边界 | 写明环境与数据前提 |
| 只验证了正常路径 | 异常路径上线才暴露 | 至少覆盖正常、边界、异常各一条 |
| 用「手动测过」代替自动化测试 | 每次改都要重测，成本递增 | 能自动化的写成测试 |
| 验收报告只写结论，不写未覆盖项 | 评审者误以为已经全覆盖 | 明确列出未覆盖项 |
