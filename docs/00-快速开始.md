# 快速开始

本文面向第一次接触本模板的开发者。读完约需 10 分钟，能让你在今天的第一个任务里就用起来。

## 一、五分钟完成环境准备

```bash
git clone https://gitee.com/hqc__com/hqc-ai-coding-work-flow.git
cd hqc-ai-coding-work-flow

# 安装 Git 钩子（二选一）
bash scripts/install-hooks.sh        # macOS / Linux / Git Bash
pwsh scripts/install-hooks.ps1       # Windows PowerShell

# 自检
node scripts/check-docs.mjs
node scripts/check-skills.mjs
```

钩子安装完成标志：执行 `git config core.hooksPath` 输出 `.githooks`。

## 二、我是谁，我该做什么

| 我的角色 | 我的主要动作 | 我产出的东西 |
| --- | --- | --- |
| 需求方 / 产品 | 提供 PRD 与原型，说清要什么、验收标准、边界 | `spec/<日期>-<主题>/` 需求目录 + `SPEC.md` 条目 |
| 开发者 | 设计、实现、自测、留证据 | 代码、测试、`docs/verification/` 证据 |
| 评审者 | 双轴评审：合规吗、做对了吗 | 评审结论 + 整改项 |
| 维护者 | 守规则本身：改规范、改门禁、定争议 | RFC 变更 + `CHANGELOG.md` |

角色可以兼任。小团队里「开发者兼评审者」是常态，但**必须由另一个人做至少一次评审**，不接受自审自过。

详细职责划分与协作节奏见 [团队协作与角色](02-团队协作与角色.md)。

## 三、第一次使用 AI 的标准开场

不要一上来就说「帮我做个客户管理」。推荐的起手式是把 AI 拉进流程：

```text
任务：客户列表支持按团队筛选
目前阶段：需求澄清
已知：见 spec/20260924-客户列表团队筛选/需求与技术对照.md
请复用 skills/spec-writer 的流程，帮我把需求补成可验收的 SPEC.md 条目。
在我确认需求之前，不要写代码。
```

关键要素只有三个：

1. **任务**：一句话说清目标。
2. **阶段**：明确当前在六阶段中的哪一步，AI 才知道该收敛还是该展开。
3. **边界**：明确这一步不许做什么（例如「不要写代码」）。

## 四、一次任务的推荐路径

```bash
# ① 需求澄清：归档原件、给需求编号、写清验收标准
node scripts/new-spec.mjs --title "客户列表团队筛选" --with-artifacts --with-verification
#    → 生成 spec/20260924-客户列表团队筛选/
#    → 把 PRD 放进 原始需求/、原型放进 原型/，只增不改
#    → 在 需求与技术对照.md 里逐条标注技术实现与影响文件
#    → 提炼稳定的需求与验收标准进 SPEC.md

# ② 方案设计：让 AI 列改动清单、接口影响、回滚方式
#    → 产出 docs/designs/20260924-客户列表团队筛选-设计.md
#    → 产出 docs/plans/20260924-客户列表团队筛选-计划.md

# ③ 实现：TDD，先写会失败的测试

# ④ 验证：把命令与原始输出存进证据目录
#    → docs/verification/20260924-客户列表团队筛选/

# ⑤ 评审：双轴评审后按结论整改

# ⑥ 交付：写 PR 说明 + 回滚方式，合并并记录
```

## 五、必须记住的四条底线

1. **没跑过的命令，不说它通过。** 先执行、再贴输出、最后下结论。
2. **密钥永远不进仓库。** 包括写进文档、注释、技能说明、示例配置里的口令。
3. **同一事实只写一处。** 写之前先判断该写进 `SPEC.md`、`MEMORY.md` 还是 `docs/`，见 [上下文与记忆治理](04-上下文与记忆治理.md)。
4. **只用仓库内技能。** 自研在 `skills/`，引入在 `.agents/skills/`；个人目录下的技能不得作为交付依据，见 [技能体系](03-技能体系.md) 第五节。
