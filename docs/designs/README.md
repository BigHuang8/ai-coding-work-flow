# 设计与方案留档

本目录存放**方案设计**，对应流水线第 ② 阶段。目的是把「为什么这么改」从聊天记录里搬到仓库里。

## 命名

`<YYYYMMDD>-<主题>-设计.md`，主题与 `spec/` 下的需求留档保持一致：

```text
spec/20260924-客户列表团队筛选.md
docs/designs/20260924-客户列表团队筛选-设计.md
docs/plans/20260924-客户列表团队筛选-计划.md
docs/verification/20260924-客户列表团队筛选/
```

## 模板

```markdown
# <主题> 设计

- 关联需求：SPEC.md#<锚点>、spec/<日期>-<主题>.md
- 作者 / 日期：

## 现状

（当前是怎么实现的，涉及哪些文件与数据）

## 目标与约束

- 目标：
- 约束：（兼容性、性能、上线窗口、不能动的部分）

## 方案

（选定方案与理由；如有备选方案，说明为什么没选）

## 改动清单

| 类型 | 文件 | 说明 |
| --- | --- | --- |
| 新增 |  |  |
| 修改 |  |  |
| 删除 |  |  |

## 接口与数据结构变化

| 项 | 变更前 | 变更后 | 是否兼容 |
| --- | --- | --- | --- |

## 数据迁移

（是否需要迁移脚本；如何回填；迁移失败的处置。无则写「无」）

## 风险评估

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |

## 回滚方式

（出问题时怎么退回去，具体到命令或操作步骤）
```

## 三条要求

1. **改动清单必须到文件级**，不要写「修改客户模块」这种粒度。
2. **回滚方式必须可执行**，写「回滚代码」不合格，要写到操作步骤。
3. **没有接口变化也要写明「无」**，空着会被误认为漏写。
