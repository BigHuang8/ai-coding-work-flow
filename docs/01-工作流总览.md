# 工作流总览

本文定义团队使用 AI 完成一次任务的**标准路径**。其他文档都是本文的展开。

## 一、六阶段流水线

```text
① 需求澄清  →  ② 方案设计  →  ③ 实现    →  ④ 验证    →  ⑤ 评审    →  ⑥ 交付
   产物 spec     产物 计划       产物 代码    产物 证据    产物 结论    产物 记录
   门禁 复述     门禁 评审       门禁 测试    门禁 复现    门禁 整改    门禁 回滚
```

每个阶段的「门禁」是一条**通过与否的判据**。门禁没过就进入下一阶段，是绝大多数返工的来源。

## 二、阶段详解

### ① 需求澄清

| 项目 | 内容 |
| --- | --- |
| 目标 | 把模糊的想法变成可验收的描述，并识别技术风险 |
| 输入 | PRD、原型图、口头需求、旧需求、线上问题 |
| 动作 | 原件归档到 `spec/<日期>-<主题>/`（只增不改）；给需求编号 `R1`、`R2`；补齐验收标准与范围外；逐条写技术实现对照；标出待确认项及确认人 |
| 产物 | `spec/<日期>-<主题>/需求与技术对照.md`、`SPEC.md` 对应条目 |
| 门禁 | **找一个没参与讨论的人，让他用自己的话复述一遍；有歧义就回去改。** |
| 常用技能 | `requirement-intake`（有 PRD / 原型时）、`spec-writer`（仅口头需求） |

### ② 方案设计

| 项目 | 内容 |
| --- | --- |
| 目标 | 在动手前暴露风险，避免写到一半推倒重来 |
| 输入 | 已确认的需求 |
| 动作 | 列出改动文件清单；写清接口与数据结构变化；说明兼容性与迁移；写明失败时的回滚方式 |
| 产物 | `docs/designs/<日期>-<主题>-设计.md`、`docs/plans/<日期>-<主题>-计划.md` |
| 门禁 | **改动清单、影响面、回滚方式三者齐全。** 缺任一项不得开工 |
| 常用技能 | `flow-orchestrator` |

### ③ 实现

| 项目 | 内容 |
| --- | --- |
| 目标 | 用最小改动实现需求，且留下能证明它工作的测试 |
| 输入 | 评审通过的设计与计划 |
| 动作 | 先写会失败的测试；小步提交；只动与任务相关的文件；边写边更新受影响的文档；编码与建表按 [后端规范](13-后端规范-Java-Spring.md)、[前端规范](14-前端规范-Vue3.md)、[数据库设计与建表规范](15-数据库设计与建表规范.md) 执行 |
| 产物 | 代码、测试、必要的文档更新 |
| 门禁 | **新增或修改的逻辑有对应测试；改动前已记录测试基线；模块校验命令通过。** |
| 常用技能 | `flow-orchestrator` + 技术栈技能 + `impact-analysis`（涉及公共代码 / 接口时） |

### ④ 验证

| 项目 | 内容 |
| --- | --- |
| 目标 | 把「我觉得没问题」换成「谁都能照着复现」 |
| 输入 | 可运行的代码 |
| 动作 | 按验收标准逐条验证；回归既有功能并与基线对比；记录命令、原始输出、截图、接口响应；记录未通过项 |
| 产物 | `docs/verification/<日期>-<主题>/` 证据 + 验收报告 |
| 门禁 | **证据可被他人按文档复现；回归结果已与基线对比。** 只贴结论不留证据视为未验证 |
| 常用技能 | `evidence-driven-verification` |

### ⑤ 评审

| 项目 | 内容 |
| --- | --- |
| 目标 | 在合并前拦下问题，而不是在线上发现 |
| 输入 | 变更集（分支或 PR）+ 需求与证据 |
| 动作 | 双轴评审：规范轴看是否合规，需求轴看是否真的做对了；输出阻断项与建议项 |
| 产物 | 评审结论（通过 / 需整改 + 清单） |
| 门禁 | **所有阻断项已整改并复核。** 建议项可以转为后续任务，但必须显式记录 |
| 常用技能 | `dual-axis-review` |

### ⑥ 交付

| 项目 | 内容 |
| --- | --- |
| 目标 | 让变更可发布、可回滚、可追溯 |
| 输入 | 评审通过的变更 |
| 动作 | 写 PR 说明（目的、验证命令、影响范围、回滚方式、关联需求）；合并；记录发布结果 |
| 产物 | PR 说明、发布记录 |
| 门禁 | **回滚方式已写明。** 没有回滚方案的变更不允许上生产 |

## 三、裁剪规则

流程的价值在于「减少返工」，不是在「制造仪式」。允许裁剪，但必须显式说明。

| 场景 | 必须做 | 可跳过 | 附加要求 |
| --- | --- | --- | --- |
| 文案 / 样式微调 | ③④⑥ | ①②⑤ | 验证证据可只保留前后对比截图 |
| 单文件 Bug 修复 | ①③④⑤ | ② | 需求澄清可合并进 issue 描述 |
| 新增接口 / 新功能 | 全部 | — | — |
| 跨模块重构 | 全部 | — | 设计稿必须含分阶段迁移路径，不接受一次性大改 |
| 线上紧急修复 | ③④⑤⑥ | ①② | 事后 3 个工作日内补 `spec/` 与 `MEMORY.md` 记录 |

裁剪时在回复或 PR 里写一行：`本次裁剪：跳过②，理由：仅修改文案。`

## 四、与 Git 的对应关系

| 阶段 | 分支 / 提交 |
| --- | --- |
| ①② | 可以在主干上直接产出文档，或使用 `docs/<主题>` 分支 |
| ③④ | 使用 `<type>/<desc>` 分支，小步提交 |
| ⑤ | 发起 PR，进入评审 |
| ⑥ | 合并到主干，删除分支，记录发布 |

## 五、端到端示例（客户列表支持按团队筛选）

| 阶段 | 实际动作 | 产物 |
| --- | --- | --- |
| ① | 归档 PRD 与原型；给需求编号 R1-R3；与产品确认仅后台生效、筛选可多选、空态文案 | `spec/20260924-客户列表团队筛选/需求与技术对照.md`、`SPEC.md` 条目 |
| ② | 确认改动：后台列表页、查询参数 DTO、SQL 条件、契约文档；回滚=移除参数 | `docs/designs/20260924-客户列表团队筛选-设计.md` |
| ③ | 先加一条会失败的契约测试（团队筛选项），再实现查询条件 | 测试 + 代码 |
| ④ | 跑接口契约测试、跑后台构建、截图筛选前后效果 | `docs/verification/20260924-客户列表团队筛选/` |
| ⑤ | 双轴评审：规范轴发现参数未加校验注解；需求轴确认多选与空态符合验收标准 | 评审结论 |
| ⑥ | PR 写明验证命令与回滚方式，合并后在 `MEMORY.md` 记一行决策 | PR + `MEMORY.md` |

## 六、常见反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 跳过 ① 直接写代码 | 做完发现理解错，全部返工 | 先复述需求再动手 |
| 跳过 ④ 直接说「已完成」 | 缺陷在评审或线上暴露 | 先跑命令，留证据 |
| 把设计和计划写进对话就开干 | 三天后没人记得为什么这么设计 | 落盘到 `docs/designs/`、`docs/plans/` |
| 一次提交几千行跨模块改动 | 评审无法有效进行 | 拆成可独立评审的小步 |
| 用「已经手动测过了」代替证据 | 不可复现，不可追溯 | 证据留档 |
