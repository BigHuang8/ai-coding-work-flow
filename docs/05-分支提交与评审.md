# 分支提交与评审

本文定义从改代码到合并的完整规则。这是日常使用频率最高的一份文档。

## 一、分支模型

采用简化的主干开发（trunk-based）：

| 分支 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 唯一主干，随时可发布 | 长期 |
| `<type>/<short-desc>` | 功能、修复、文档 | 合并后删除 |

规则：

1. 分支存在时间**不超过 3 个工作日**。超过说明任务拆得不够细。
2. 每天至少从 `main` 同步一次，减少冲突面积。
3. 不建长期分支，不建个人常驻分支。

## 二、分支命名

```text
<type>/<short-desc>
```

- `type` 与提交类型一致：`feat` `fix` `docs` `refactor` `perf` `test` `chore`
- `short-desc` 用小写英文与连字符，2-4 个单词，能看出改什么

示例：`feat/customer-team-filter`、`fix/token-expire-jump`、`docs/verification-guide`

反例：`dev`、`test2`、`nietao`、`feature-20260924`（无信息量或过于宽泛）。

## 三、提交信息

格式：

```text
type(scope): subject
```

| 部分 | 要求 |
| --- | --- |
| `type` | 必填，取值见下表 |
| `scope` | 必填，模块名小写，如 `customer`、`auth`、`admin`、`workflow` |
| `subject` | 中文，动词开头，不加句号，不超过 50 字 |

| type | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `style` | 不影响逻辑的格式调整 |
| `refactor` | 重构（行为不变） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建或依赖 |
| `ci` | 流水线或钩子 |
| `chore` | 杂项 |
| `revert` | 回滚 |

正例：

```text
feat(customer): 客户列表支持按团队多选筛选
fix(auth): 令牌过期后未跳转登录页
docs(workflow): 补充证据留档的目录规范
```

反例：

```text
更新代码                    # 缺少 type/scope，且无信息量
feat(customer): 修改了一些东西   # subject 不具体
fix: 修复 bug               # 缺少 scope
```

提交粒度：**一次提交只做一件事**。把「修 Bug」和「顺手重构」放在一个提交里，回滚时无法只回滚一半。

## 四、PR 说明

模板见 `.github/PULL_REQUEST_TEMPLATE.md`。五个必填项：

| 字段 | 说明 |
| --- | --- |
| 变更目的 | 解决什么问题，关联哪个需求（`SPEC.md` 锚点或 `spec/` 文件） |
| 验证命令 | 实际执行过的命令与结果；**未执行的不要写** |
| 影响范围 | 影响的模块、接口、数据结构、配置 |
| 回滚方式 | 出问题时怎么退回去 |
| 截图 / 证据 | 涉及界面的必附；链接到 `docs/verification/` 目录 |

## 五、评审清单

评审采用双轴结构，技能说明见 `skills/dual-axis-review/SKILL.md`。

### 规范轴（是否合规）

- [ ] 提交信息与分支命名符合本文件规则
- [ ] 模块校验命令通过（`npm run validate` / `mvn test` 等）
- [ ] 未修改与任务无关的文件
- [ ] 无新增的静默抑制（`@ts-ignore`、`# noqa`、注释掉的测试）
- [ ] 无密钥、口令、真实数据进入版本库
- [ ] 文档已同步（`SPEC.md` / `MEMORY.md` / `docs/` 至少一处）

### 需求轴（是否做对）

- [ ] 逐条对照验收标准，确认每条都被满足
- [ ] 范围外的事确实没做（没有偷偷扩大范围）
- [ ] 边界与异常路径有处理（空值、越界、超时、并发）
- [ ] 有对应测试，且测试能体现验收标准
- [ ] 证据可复现（换成评审者本人能跑出同样结果）

### 结论格式

```text
结论：需整改
阻断项：
1. src/.../CustomerQueryService.ts:88 团队筛选未处理空数组，会导致全表查询
2. 缺少团队筛选的契约测试
建议项：
1. 筛选参数可考虑封装为对象，减少后续扩展改动面（转任务 #123）
```

**阻断项与建议项必须分开。** 把建议项当阻断项会拖慢交付，把阻断项当建议项会把风险带上线。

## 六、合并策略

| 场景 | 策略 |
| --- | --- |
| 单人功能分支 | Squash 合并，提交信息沿用 PR 标题 |
| 多人协作分支 | Merge 合并，保留各人提交 |
| 回滚 | 用 `revert` 生成反向提交，不要强推主干 |

合并前必须满足：

1. 评审结论为「通过」，无未整改的阻断项。
2. CI 通过。
3. 分支已同步最新主干，冲突已解决。

## 七、常见问题

**Q：紧急修复能不能先合再补证据？**
A：可以，但必须在 PR 中写明「事后补证」，并在 3 个工作日内补齐 `spec/` 与证据目录。

**Q：一个人的项目还需要评审吗？**
A：需要替代方案：等 30 分钟冷却期后自审，且必须留下双轴检查清单的填写记录。冷却期的作用是让作者脱离「刚写完」的心态。

**Q：评审者没空怎么办？**
A：约定 24 小时响应 SLA。超时后可由维护者指定替代评审者，不允许因为没人评审就直接合并。
