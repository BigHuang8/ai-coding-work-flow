# 分支提交与评审

本文定义从改代码到合并的完整规则。这是日常使用频率最高的一份文档。

## 一、分支模型

采用简化的主干开发（trunk-based）：

| 分支 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 唯一主干，随时可发布 | 长期 |
| `<type>/<short-desc>` | 功能、修复、文档 | 合并后删除 |

规则：

1. 分支存在时间**不超过 3 个工作日**。超过说明任务拆得不够细。
2. 每天至少从 `main` 同步一次，减少冲突面积。
3. 不建长期分支，不建个人常驻分支。

## 二、分支命名

```text
<type>/<short-desc>
```

- `type` 与提交类型一致：`feat` `fix` `docs` `refactor` `perf` `test` `chore`
- `short-desc` 用小写英文与连字符，2-4 个单词，能看出改什么

示例：`feat/customer-team-filter`、`fix/token-expire-jump`、`docs/verification-guide`

反例：`dev`、`test2`、`nietao`、`feature-20260924`（无信息量或过于宽泛）。

## 三、分支创建与同步实操

```bash
# 1. 先同步主干，再从最新主干切分支，避免从过期代码起步
git switch main && git pull --ff-only
git switch -c feat/customer-team-filter

# 2. 每天至少一次把主干变更带进来（个人特性分支用 rebase 保持线性）
git fetch origin
git rebase origin/main

# 3. rebase 出现冲突：解决后标记，再继续
git add <解决后的文件>
git rebase --continue

# 4. 首次推送并建立上游关联
git push -u origin feat/customer-team-filter
```

Rebase 还是 Merge，按分支是否已共享来选：

| 场景 | 用 | 原因 |
| --- | --- | --- |
| 个人特性分支同步主干 | `rebase` | 历史线性，评审时 diff 干净 |
| 分支已被他人基于开发 | `merge` | rebase 会重写别人已依赖的提交 |
| 主干、长命共享分支 | `merge` | **永不改写共享历史** |
| 合入主干 | 见第七节合并策略 | — |

安全规则：

1. **只 rebase 自己的、未被他人使用的分支**；一旦有人基于它工作，改用 `merge`。
2. 分支存活不超过 3 个工作日，超时就拆小，不要靠「反正能 rebase」硬撑。
3. 强推只允许用于个人特性分支，且必须用 `git push --force-with-lease`；主干一律禁止强推（`--force-with-lease` 会在他人推送后拒绝执行，比 `--force` 安全）。
4. 切换任务或评审他人代码前，先 `git status` 确认工作区干净，避免把无关改动带进别人的分支。

## 四、提交信息

格式：

```text
type(scope): subject
```

| 部分 | 要求 |
| --- | --- |
| `type` | 必填，取值见下表 |
| `scope` | 必填，模块名小写，如 `customer`、`auth`、`admin`、`workflow` |
| `subject` | 中文，动词开头，不加句号，不超过 50 字 |

| type | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `style` | 不影响逻辑的格式调整 |
| `refactor` | 重构（行为不变） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建或依赖 |
| `ci` | 流水线或钩子 |
| `chore` | 杂项 |
| `revert` | 回滚 |

正例：

```text
feat(customer): 客户列表支持按团队多选筛选
fix(auth): 令牌过期后未跳转登录页
docs(workflow): 补充证据留档的目录规范
```

反例：

```text
更新代码                    # 缺少 type/scope，且无信息量
feat(customer): 修改了一些东西   # subject 不具体
fix: 修复 bug               # 缺少 scope
```

提交粒度：**一次提交只做一件事**。把「修 Bug」和「顺手重构」放在一个提交里，回滚时无法只回滚一半。

## 五、合并请求说明

合并请求在 GitHub 上叫 PR、在 GitLab 上叫 MR，本文档统一写作「合并请求」，操作按各平台习惯来。

模板见 `.github/PULL_REQUEST_TEMPLATE.md`（GitHub）、`.gitlab/merge_request_templates/Default.md`（GitLab）
或 `.gitee/PULL_REQUEST_TEMPLATE.md`（Gitee），三份内容一致。五个必填项：

GitLab 那份为什么叫 `Default.md`：GitLab 用**文件名当模板名**，显示在新建合并请求的「Choose a template」下拉框里；
命名为 `Default`（大小写不敏感）的那份才会**自动套用**，不必每次手动选。要再加别的模板（例如 `Hotfix.md`），
放进同一个 `.gitlab/merge_request_templates/` 目录即可，下拉框里会自动出现，不影响 `Default.md` 的默认行为。

| 字段 | 说明 |
| --- | --- |
| 变更目的 | 解决什么问题，关联哪个需求（`SPEC.md` 锚点或 `spec/` 文件） |
| 验证命令 | 实际执行过的命令与结果；**未执行的不要写** |
| 影响范围 | 影响的模块、接口、数据结构、配置 |
| 回滚方式 | 出问题时怎么退回去 |
| 截图 / 证据 | 涉及界面的必附；链接到 `docs/verification/` 目录 |

## 六、评审清单

评审采用双轴结构，技能说明见 `skills/dual-axis-review/SKILL.md`。

> 配图见 [`assets/dual-axis-review.png`](../assets/dual-axis-review.png)：规范轴、需求轴、结论格式与常见反模式。

### 规范轴（是否合规）

- [ ] 提交信息与分支命名符合本文件规则
- [ ] 模块校验命令通过（`npm run validate` / `mvn test` 等）
- [ ] 未修改与任务无关的文件
- [ ] 无新增的静默抑制（`@ts-ignore`、`# noqa`、注释掉的测试）
- [ ] 无密钥、口令、真实数据进入版本库
- [ ] 未引入仓库外技能依赖；新增自研技能已登记 `skills/README.md`，引入技能已登记 `skills-lock.json`
- [ ] 文档已同步（`SPEC.md` / `MEMORY.md` / `docs/` 至少一处）

### 需求轴（是否做对）

- [ ] 逐条对照验收标准，确认每条都被满足
- [ ] 范围外的事确实没做（没有偷偷扩大范围）
- [ ] 边界与异常路径有处理（空值、越界、超时、并发）
- [ ] 有对应测试，且测试能体现验收标准
- [ ] 证据可复现（换成评审者本人能跑出同样结果）

### 结论格式

```text
结论：需整改
阻断项：
1. src/.../CustomerQueryService.ts:88 团队筛选未处理空数组，会导致全表查询
2. 缺少团队筛选的契约测试
建议项：
1. 筛选参数可考虑封装为对象，减少后续扩展改动面（转任务 #123）
```

**阻断项与建议项必须分开。** 把建议项当阻断项会拖慢交付，把阻断项当建议项会把风险带上线。

## 七、合并策略

| 场景 | 策略 |
| --- | --- |
| 单人功能分支 | Squash 合并，提交信息沿用 PR 标题 |
| 多人协作分支 | Merge 合并，保留各人提交 |
| 回滚 | 用 `revert` 生成反向提交，不要强推主干 |

合并前必须满足：

1. 评审结论为「通过」，无未整改的阻断项。
2. CI 通过。
3. 分支已同步最新主干，冲突已解决。

## 八、常见 Git 操作与急救

日常操作：

| 目的 | 命令 |
| --- | --- |
| 只提交部分改动（一个文件里的几处） | `git add -p` |
| 看清将要提交什么 | `git diff --cached` |
| 提交信息写错（尚未推送） | `git commit --amend` |
| 临时切换任务 | `git stash push -m "customer-filter 半成品"` / `git stash pop` |
| 撤销未推送的提交但保留改动 | `git reset --soft HEAD~1` |
| 撤销已推送的提交 | `git revert <sha>`（生成反向提交，**不要** reset 主干） |
| 定位某行是谁改的 | `git blame -L 10,20 <文件>` |
| 定位哪次提交引入问题 | `git bisect start` / `git bisect good` / `git bisect bad` |
| 误删分支后找回 | `git reflog` 找到 SHA 后 `git switch -c <分支> <sha>` |
| 合并后检查缩进 / 冲突残留 | `git diff --check` |

危险操作与替代方案：

| 危险操作 | 后果 | 替代做法 |
| --- | --- | --- |
| 向主干 `git push --force` | 覆盖他人提交，无法追溯 | `git revert` 生成反向提交 |
| `git reset --hard` | 未提交改动直接丢失 | 先 `git stash`，或只加 `--soft` |
| `git checkout .` / `git restore .` | 清空工作区未提交改动 | 先 `git diff` 确认，或先 stash |
| `--no-verify` 绕过钩子 | 门禁失效，问题进主干 | 修代码，或走 RFC 改规则 |
| 在主干上直接改代码 | 冲突与回滚都变困难 | 切分支，哪怕是 5 分钟的小改动 |

冲突处理原则：**不猜**。看不懂对方的意图就找人问，不要为了「让冲突消失」删掉别人的逻辑；解决后必须跑一次校验命令，并在 PR 里说明冲突涉及哪些文件。

## 九、常见问题

**Q：紧急修复能不能先合再补证据？**
A：可以，但必须在 PR 中写明「事后补证」，并在 3 个工作日内补齐 `spec/` 与证据目录。

**Q：一个人的项目还需要评审吗？**
A：需要替代方案：等 30 分钟冷却期后自审，且必须留下双轴检查清单的填写记录。冷却期的作用是让作者脱离「刚写完」的心态。

**Q：评审者没空怎么办？**
A：约定 24 小时响应 SLA。超时后可由维护者指定替代评审者，不允许因为没人评审就直接合并。
