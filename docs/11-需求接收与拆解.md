# 需求接收与拆解

产品经理给了需求文档和原型图，这份文档说明**原件放哪、技术实现写在哪、怎么走完从收到材料到开工的全过程**。

这是流水线第 ① 阶段（需求澄清）在有正式交付物场景下的展开。流程对应技能 `skills/requirement-intake/SKILL.md`。

## 一、核心原则：原件不动，技术另记

```
PRD 原件（只增不改）  ──┐
                         ├──→  需求与技术对照.md  ──→  SPEC.md 条目
原型件（只增不改）    ──┘        （技术实现写这里）      （需求权威来源）
```

三条铁律：

1. **原件一律不改。** PRD 和原型是证据，改了就无法追溯「当初要求的是什么」。需求变了，存新版本，不覆盖旧的。
2. **技术实现不写进 PRD。** 写在「需求与技术对照」里，用 `R1`、`R2` 编号与需求条目挂钩。这样 PRD 保持对外部可交付，技术内容保持对内部可追溯。
3. **二进制原件旁要有 markdown 转换件。** `.docx`、`.pdf` 里的话 AI 检索不到；转一份 `.md` 放在原件旁，内容冲突时以原件为准。

## 二、原件放在哪

```text
spec/<YYYYMMDD>-<主题>/
├── 需求与技术对照.md      # 主文档：来源、需求条目、技术实现对照、待确认项
├── 原始需求/             # PRD 原件（docx / pdf / xlsx / md）、需求变更通知、IM 截图
└── 原型/                 # 原型导出件（Axure / Figma / 墨刀 HTML 或图片）、关键页面截图
```

主题命名与 `docs/verification/` 下的验收目录保持一致，形成同一条追溯链：

```text
spec/20260924-客户列表团队筛选/          需求输入
docs/designs/20260924-客户列表团队筛选-设计.md   方案
docs/plans/20260924-客户列表团队筛选-计划.md     计划
docs/verification/20260924-客户列表团队筛选/     证据
```

**为什么不用 `docs/` 根目录？** 把 PRD 直接丢在 `docs/` 根目录（很多项目都这么做）有三个问题：找不到是哪次需求、无法追溯版本、和规范文档混在一起。放进按日期命名的需求目录后，一个需求的一切都在一处。

## 三、完整流程（七步）

### 步骤 1：接收与归档

```bash
node scripts/new-spec.mjs --title "客户列表团队筛选" --with-artifacts --with-verification
```

然后：

- [ ] PRD 原件放进 `原始需求/`，**保留原始文件名**
- [ ] 原型件放进 `原型/`，页面截图用页面名命名（如 `客户列表-默认.png`）
- [ ] 在「原件清单」登记：原件、类型、版本 / 日期、存放位置
- [ ] 二进制原件旁补一份 markdown 转换件（命名 `<原名>.md`）

### 步骤 2：通读并编号

给每条需求一个编号 `R1`、`R2`……，写清出处（PRD 第几节 / 原型第几页）。

**为什么要编号：** 后续设计稿、提交信息、评审结论、验收报告都引用同一个编号，追溯链才闭合。没有编号，讨论时只能说「那个筛选的需求」，几天后就对不上。

### 步骤 3：写需求条目

逐条填写「需求（来源出处）」与「验收标准」：

| 编号 | 需求（来源出处） | 验收标准 | 范围外 |
| --- | --- | --- | --- |
| R1 | 团队筛选支持多选（PRD 第 3.2 节） | 选中两个团队时结果为两团队客户并集；不选等于全部 | 不支持按标签组合筛选 |

验收标准必须可判定。**出现「友好」「流畅」「合理」这类词就是不合格**，改写成可测量的条件。

需求条目写法与 `skills/spec-writer/SKILL.md` 一致，两个技能配合使用。

### 步骤 4：填技术实现对照

这一步就是「在需求文档里加入技术实现」的落地方式：

| 编号 | 技术实现要点 | 影响文件 / 接口 | 已有基础 | 预估工作量 | 风险 |
| --- | --- | --- | --- | --- | --- |
| R1 | 查询对象加 `teamIds` 数组；Service 层拼 `IN` 条件；为空时不加该条件 | `CustomerQueryRequest`、`CustomerQueryService`、`CustomerController`；接口新增可选参数 | 复用现有 `PageQuery` | 小 | 团队数量多时 `IN` 列表过长 |

填写要求：

- **技术实现要点**：说清「改哪一层、用什么机制」，不写代码。写代码是 ③ 阶段的事。
- **影响文件 / 接口**：到文件或接口级；涉及接口变更必须同步 `docs/API_CONTRACT.md`。
- **已有基础**：能否复用现有实现。这一列能挡掉大量重复造轮子。
- **风险**：兼容性、数据迁移、性能、第三方依赖。

### 步骤 5：澄清与确认

把不确定项写进「待确认项」表，写明**由谁确认**。与产品对齐后更新状态。

**不确定的不要猜。** 用假设填空会把错误固化进文档，代价远高于多问一句。

### 步骤 6：提炼进 SPEC.md

把已经稳定的需求与验收标准写进 `SPEC.md` 对应模块，并**反向链接到需求目录**：

```markdown
### 1.1 客户列表

- 需求：支持按团队、状态筛选，支持关键字搜索
- 验收标准：
  1. 团队筛选支持多选，不选等于全部
  2. 筛选结果为空时展示空态文案「暂无符合条件的客户」
- 范围外：不支持按标签组合筛选
- 关联：spec/20260924-客户列表团队筛选/
```

`SPEC.md` 是需求的**权威来源**，`spec/` 目录是**输入留档**。两者的分工见 `docs/04-上下文与记忆治理.md`。

### 步骤 7：交接设计

进入流水线 ② 阶段，产出 `docs/designs/` 与 `docs/plans/`。设计稿应当**逐条回应技术对照表里的风险项**。

## 四、原型的使用方式

原型不只是阅读理解材料，它是**验收基准**：

| 阶段 | 原型的用途 |
| --- | --- |
| ① 需求澄清 | 确认交互细节，把「原型上说不清的部分」列入待确认项 |
| ② 方案设计 | 评估实现成本，识别与现有组件的差异 |
| ③ 实现 | 对齐布局、状态、文案 |
| ④ 验证 | 做**原型 vs 实际**对比图，放进 `docs/verification/<主题>/assets/` |
| ⑤ 评审 | 需求轴按原型逐页核对 |

对比图命名建议：`<页面名>-comparison.png`，与原型件同名，便于评审时左右对照。

**注意：** 原型与实现不一致时，不要默认「实现错了」。先确认是否属于待确认项，再决定改实现还是记录为已知差异。差异必须显式记录，不能默默放过。

## 五、裁剪

| 场景 | 做法 |
| --- | --- |
| 有正式 PRD + 原型 | 完整走七步 |
| 只有口头/IM 需求，无原件 | 用 `spec-writer`；建档时**不加** `--with-artifacts` |
| 一次性小改动 | 需求条目只写一条，技术对照可只填「影响文件」与「工作量」 |
| 线上紧急修复 | 先修后补：3 个工作日内补齐需求目录与原件 |

## 六、反模式

| 反模式 | 问题 |
| --- | --- |
| PRD 直接放 `docs/` 根目录 | 无法追溯是哪次需求、哪一版 |
| 把技术方案写进 PRD 原件 | 原件被污染，外部交付物失真，且版本无法回溯 |
| 收到新版本直接覆盖旧原件 | 丢失历史，无法解释需求为何变化 |
| 只存 `.docx` 不转 markdown | AI 检索不到，每次都要人工转述一遍 |
| 需求不编号 | 设计、提交、评审、验收无法引用同一条需求 |
| 原型差异不记录 | 上线后才发现与原型不符，返工成本最高 |
| 待确认项用假设填空 | 错误被固化进文档，后期大规模返工 |
