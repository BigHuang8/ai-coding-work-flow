# 上下文与记忆治理

AI 的表现很大程度取决于「它读到了什么」。文档写重了会互相矛盾，写漏了会反复重来。本文定义信息的归位规则。

## 一、为什么必须治理

三个真实问题：

1. **上下文预算有限。** 一次任务能读的内容是有限的，把细节堆进入口文件，会挤掉真正重要的规则。
2. **重复即矛盾。** 同一件事写两处，改动时只会改一处，AI 读到旧的那处就会做错。
3. **无索引即无记忆。** 没有索引，新会话的 AI 和新人一样，都要从零问一遍。

## 二、五类文档的分工

| 文件 | 回答的问题 | 生命周期 | 谁维护 |
| --- | --- | --- | --- |
| `AGENTS.md` | 规则在哪里、底线是什么 | 长期稳定 | 维护者 |
| `SPEC.md` | 要求做什么、怎么算做完 | 与产品同步演进 | 需求方 + 开发者 |
| `MEMORY.md` | 为什么这么定、当前有效口径 | 只增不改（改则标注） | 开发者 |
| `docs/*` | 具体怎么做、检查什么 | 长期稳定 | 维护者 + 各模块负责人 |
| `spec/` + `docs/verification/` | 这次改了什么、凭什么说改对了 | 一次任务一份，定稿后不回改 | 开发者 |

**判断口诀**：

- 换一个项目也成立 → 写 `docs/`
- 只对本项目成立、且长期有效 → 写 `SPEC.md`
- 只对本项目成立、且是「为什么」→ 写 `MEMORY.md`
- 只对这一次任务成立 → 写 `spec/` 与 `docs/verification/`

## 三、SPEC.md 的写法

`SPEC.md` 是**需求的权威来源**。结构建议：

```markdown
# 需求规格说明书

> 本文件是需求的唯一权威来源。与旧文档、聊天记录冲突时，以本文件为准。

## 1. 模块：客户管理

### 1.1 客户列表

- 需求：支持按团队、状态筛选，支持关键字搜索
- 验收标准：
  1. 团队筛选支持多选，不选等于全部
  2. 筛选结果为空时展示空态文案「暂无符合条件的客户」
  3. 列表默认每页 20 条，支持切换 50 / 100
- 范围外：不支持按标签组合筛选（后续需求）
- 关联：spec/20260924-客户列表团队筛选.md
```

要点：

- **验收标准必须可判定**。「体验流畅」不是验收标准，「首屏渲染 < 1 秒」才是。
- **写明范围外**，这是减少返工最有效的一句话。
- **每条需求关联对应的 `spec/` 文件**，形成可追溯链。
- 需求变更时**直接改 `SPEC.md`**，并在 `MEMORY.md` 记一行变更原因，不要另开新文件。

## 四、MEMORY.md 的写法

`MEMORY.md` 是**决策索引**，不是需求文档。每条记录回答「为什么这么定」，并给出现状。

```markdown
## 认证与入职

- 2026-09-22：电子签采用「线下短信通知 + App 签署指引 + 后台审核」，不接第三方电子签。
  原因：采购周期与合规要求。影响：签署状态需人工推进，后台需提供审核入口。
  关联：SPEC.md#认证与入职模块
```

三条要求：

1. **带日期**。没有日期，三个月后无法判断新旧。
2. **带原因**。只写结论等于没有记忆，下次还会被推翻。
3. **带影响与关联**。让别人知道这条决策会碰到哪些代码或文档。

已失效的条目**不要删除**，改为标注 `（已废止，2026-10-01 起由 XXX 取代）`。历史决策的价值在于解释「为什么不再是那样」。

## 五、spec/ 的留档规范

目录：`spec/<YYYYMMDD>-<主题>/`，例如 `spec/20260924-客户列表团队筛选/`。

```text
spec/20260924-客户列表团队筛选/
├── 需求与技术对照.md     主文档：原件清单、需求条目、技术实现对照、待确认项
├── 原始需求/             PRD 原件（docx / pdf / xlsx / md），只增不改
└── 原型/                 原型件与关键页面截图，只增不改
```

规则：

- **原件一律不改**。需求变更时另存新版本并在清单追加一行，不覆盖旧版。
- **技术实现写在对照表里**，用 `R1`、`R2` 编号关联需求条目，不要写回 PRD 原件。
- **二进制原件旁留一份 markdown 转换件**，否则 AI 检索不到；内容冲突时以原件为准。
- 改需求请改 `SPEC.md`，不要回改 `spec/` 目录。
- 一个需求一个目录；轻量需求可退回单文件形态 `spec/<日期>-<主题>.md`。
- 需求被推翻时，在主文档顶部加一行 `> 状态：已废止（原因、日期）`。

完整流程见 [需求接收与拆解](11-需求接收与拆解.md)。

## 六、上下文预算建议

给 AI 的上下文要有取舍。经验值：

| 场景 | 建议加载 |
| --- | --- |
| 日常开发 | `AGENTS.md` + `docs/01` + 目标模块的规范文档 + 相关代码 |
| 需求澄清 | `AGENTS.md` + `skills/spec-writer` + 同主题历史 `spec/` |
| 评审 | `AGENTS.md` + `docs/05` + `skills/dual-axis-review` + 变更 diff |
| 排障 | `AGENTS.md` + `MEMORY.md` 相关条目 + 日志与代码 |

**不要**把整个 `docs/` 一次性塞给 AI；也不要只给一句话需求就期待好结果。

## 七、过期治理

每季度做一次（可由维护者发起，30 分钟）：

1. 扫描 `MEMORY.md`：有没有互相矛盾的条目？有没有该废止未标注的？
2. 扫描 `docs/`：有没有描述与现实不符的步骤？
3. 扫描 `spec/`：超过半年且无关联实现的需求，标记归档。
4. 扫描 `skills/`：哪些技能 3 个月没被使用？考虑退役。
5. 完成后在 `CHANGELOG.md` 记一行。

## 八、反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 把教程写进 `AGENTS.md` | 入口臃肿，重要规则被淹没 | 入口只放索引与硬性规则 |
| 需求同时写在 `SPEC.md` 和 `docs/` | 两处不一致，AI 随机读到一份 | 需求只在 `SPEC.md`，`docs/` 只引用 |
| `MEMORY.md` 只记结论不记原因 | 决策被反复推翻 | 带日期、原因、影响 |
| 改需求时覆盖 `spec/` 原文 | 丢失原始意图，无法复盘 | 改 `SPEC.md`，`spec/` 保留原文 |
| 验收证据只有一句「已通过」 | 不可复现，等于没验证 | 见 [验收与证据留档](06-验收与证据留档.md) |
