# 团队协作与角色

AI 助手改变的是「谁来做」，不改变「谁负责」。本文定义协作角色、职责边界与协作节奏。

## 一、四个角色

| 角色 | 一句话职责 | 不负责 |
| --- | --- | --- |
| 需求方 | 说清楚要什么、怎么算做完 | 不决定技术实现 |
| 开发者 | 把需求变成可验证的实现 | 不单方面扩大范围 |
| 评审者 | 在合并前拦下问题 | 不替开发者改代码（可给建议补丁） |
| 维护者 | 守规则本身：改规范、改门禁、定争议 | 不仲裁具体业务细节 |

小团队可兼任，但三条硬约束必须保留：

1. **不能自审自过**：任何进入主干的变更，至少有一名非作者参与评审。
2. **不能自定需求**：开发者不得单方面扩大或收缩验收标准，需需求方确认。
3. **不能自改门禁**：为了让自己这次通过而放宽规则属于违规，必须走 RFC。

## 二、职责矩阵（RACI 精简版）

`R`=执行，`A`=最终负责，`C`=需咨询，`I`=需告知

| 活动 | 需求方 | 开发者 | 评审者 | 维护者 |
| --- | --- | --- | --- | --- |
| 需求澄清 | A/R | C | I | I |
| 方案设计 | C | A/R | C | I |
| 实现与自测 | I | A/R | I | I |
| 验证与留证 | C | A/R | C | I |
| 评审 | I | C | A/R | I |
| 交付与回滚 | I | A/R | C | I |
| 流程与技能变更 | C | C | C | A/R |

## 三、协作节奏

### 需求澄清（异步优先）

- 默认以需求目录 `spec/<日期>-<主题>/` 为载体异步进行，减少会议。
- 需求方提供 PRD 与原型，写「要什么 / 不要什么 / 怎么算做完」。
- 开发者在「需求与技术对照」中逐条补技术实现与影响文件，并写「技术风险 / 待确认项 / 需谁确认」。
- **原件只增不改**：需求变更时存新版本并追加清单行，不覆盖旧版；技术内容不写回 PRD。
- 收口标准：门禁「第三方能复述且无歧义」通过。

### 设计与计划评审（30 分钟内）

- 只评审三件事：改动清单、影响面（接口 / 数据 / 兼容性）、回滚方式。
- 不在这个环节讨论代码风格，那是评审阶段的事。

### 代码评审（24 小时内响应）

- 使用 `skills/dual-axis-review` 的双轴结构，避免「看起来还行」这类无效结论。
- 输出必须包含：阻断项（必须改）、建议项（可转任务）、结论（通过 / 需整改）。

### 验收（发布前）

- 由非开发者按验收标准逐条核对证据目录。
- 证据不能满足复现要求时，退回 ④ 阶段。

## 四、任务归属与并行协调

### 4.1 谁在开发：靠 Git 事实，不靠手工台账

归属信息全部从 Git 派生，不需要额外的排期表：

| 问题 | 事实来源 |
| --- | --- |
| 这个分支谁负责 | 分支上最近的提交作者（`git log --format=%an`） |
| 这次改动对应哪个需求 | 分支改动中包含的 `spec/<日期>-<主题>/` 目录名 |
| 谁该评审这份代码 | `CODEOWNERS`（GitHub 放 `.github/`，GitLab 放仓库根；Gitee 用仓库设置的评审人） |
| 谁提出的需求 | `spec/<日期>-<主题>/需求与技术对照.md` 的「来源元信息」 |

前提：每人本地配置真实姓名与公司邮箱，否则归属失真。

```bash
git config user.name "张三"
git config user.email "zhangsan@example.com"
```

**不要手写任务台账。** 多人同时改会冲突，且没人愿意持续维护，一周后就是过期数据。看板从 Git 自动生成。

### 4.2 任务占用看板

```bash
node scripts/tasks.mjs                  # 查看活跃分支、负责人与重叠情况
node scripts/tasks.mjs --check          # 只看当前分支是否与他人重叠
node scripts/tasks.mjs --active-days 3  # 只看最近 3 天有提交的分支
```

统计口径是「最近 N 天内该分支**自身**提交所触及的文件」（`git log --since=N --not <主干>`），两个条件缺一不可：

- 不加 `--not <主干>`：主干上的旧提交会被算进每个分支，新仓库里人人都在改 `AGENTS.md`、`scripts/`；
- 只按 `主干..分支` 取全量差异：分支寿命一长，几百个历史差异会被算成本次改动，同样全是误报。

输出示例：

```text
● feat/customer-team-filter
  负责人：张三
  最近提交：2026-09-24  feat(customer): 客户列表支持按团队筛选
  需求主题：20260924-客户列表团队筛选
  近期改动文件：6 个

⚠️  代码文件重叠 1 处（需要沟通）：
  hfzh-server/.../CustomerQueryService.java
    涉及分支：origin/feat/customer-team-filter、origin/fix/team-scope
```

### 4.3 长命分支要排除

首先确认「主干」是哪一个分支。多数仓库是 `main` / `master`，但有些团队真正的集成分支是 `int` / `develop`，此时 `master` 早已落后几百个提交——**基线选错，看板全是噪声**。在仓库根的 `workflow.config.json` 固定下来，脚本会优先读它：

```json
{ "trunkBranch": "origin/int" }
```

如果某个分支的「自身改动」超过 200 个文件，看板会把它列为**长命 / 严重分叉分支**并排除在重叠分析之外，同时提示你检查基线是否正确。看到这个提示时，先别怀疑同事：八成是基线选错了。

`int`、`develop`、`release/*` 这类长命共享分支本来就包含所有人的改动，参与统计只会产生噪声。写进仓库根的 `.tasksignore`：

```text
int
develop
release/*
```

排除后看板只显示短命的特性分支，信号才清晰。

**这本身就是一个征兆**：如果你需要排除很多分支，说明分支模型该收敛了——长命共享分支正是「看不出谁在做什么」的根因之一。

### 4.4 发现重叠怎么办

按顺序处理，不要直接开干：

1. **先沟通**：确认是不是真的在做同一件事。是同一件事 → 合并为一个人做，另一个人改做别的。
2. **划边界**：不同的事但改了同一批文件 → 按文件拆分，各自只改属于自己的文件。
3. **接口先行**：存在调用关系 → 先把签名与数据结构提交，再各自实现。
4. **契约文件让路**：`docs/API_CONTRACT.md` 这类共享文件同一时间只允许一个人改。
5. **缩短分支**：分支超过 3 个工作日就拆小或尽快合并。

### 4.5 三条硬规则

1. **按文件划分，不按功能划分。** 任务拆分粒度到文件级，例如「A 负责 `CustomerQueryService`，B 负责 `CustomerController`」，而不是「A 负责前半段，B 负责后半段」。
2. **接口先行。** 并行任务之间存在调用关系时，先把接口签名与数据结构定下来并提交，再各自实现。
3. **契约文件单一写入者。** `docs/API_CONTRACT.md` 这类共享文件同一时间只允许一个人修改，其余人只读。

关于「改动会不会弄坏已有功能」，见 [影响面与回归防护](12-影响面与回归防护.md)。

## 五、AI 助手的定位

| 可以做 | 不可以做 |
| --- | --- |
| 起草需求、设计、计划、测试、文档 | 决定验收标准（需需求方确认） |
| 执行验证并整理证据 | 代替人工验收签字 |
| 提出评审意见与整改建议 | 自审自过、自行合并 |
| 批量机械改动（重命名、迁移调用） | 未理解根因就「试试看」式修改 |

给 AI 的指令请始终携带：**任务、当前阶段、边界**。示例见 [快速开始](00-快速开始.md) 第三节。

## 六、新成员上手路径

| 时间 | 动作 | 完成标志 |
| --- | --- | --- |
| 第 1 天上午 | 读 `README.md`、`docs/00-快速开始.md`、`docs/01-工作流总览.md` | 能说出六阶段名称与各自门禁 |
| 第 1 天下午 | 装钩子、跑通 `node scripts/check-docs.mjs` | 本地校验通过 |
| 第 2 天 | 独立完成一个「文案微调」类任务，走裁剪流程 | PR 被合并 |
| 第 1 周 | 独立完成一个「单文件 Bug 修复」，含证据留档 | 评审一次通过 |
| 第 2 周 | 参与一次评审，输出双轴结论 | 评审结论被采纳 |

导师职责：第 1 周内至少复核新成员的一次证据目录，指出版本、命令、复现步骤上的问题。

## 七、冲突与升级

| 冲突类型 | 处理方式 |
| --- | --- |
| 需求理解不一致 | 回到 ① 阶段，由需求方书面确认，写进 `SPEC.md` |
| 技术方案分歧 | 在设计与计划评审时定，写入 `docs/designs/` 并记一行到 `MEMORY.md` |
| 规范与现实冲突 | 提 RFC：说明现状、痛点、备选方案、影响面，由维护者裁定 |
| 有人绕过流程 | 不追究个人，先补门禁；连续两次同类绕过则升级到维护者 |
