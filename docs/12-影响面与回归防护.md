# 影响面与回归防护

回答一个问题：**我改的东西，会不会弄坏别人已经跑通的功能？**

这是流水线第 ③④ 阶段的展开，对应技能 `skills/impact-analysis/SKILL.md`。

## 一、为什么「跑一遍测试」不够

三个真实失效场景：

1. 改动前测试本来就是红的，改完后跑同样的测试失败，分不清是谁弄红的。
2. 只跑了新功能的测试，没跑调用方既有功能的测试。
3. 改了公共方法，测试覆盖率再高也测不到「所有调用方的业务语义是否仍然正确」。

对应三个动作：**记录基线、反查调用方、回归验证**。

## 二、基线：动手前先记录现状

在**干净的工作区**跑一次完整校验，把结果记下来：

```bash
git status        # 确认没有未提交的改动干扰判断
npm run validate  # 或 mvn test，按技术栈
```

把结果记进需求目录的「处理记录」或验收证据：

| 项 | 基线结果 |
| --- | --- |
| 校验命令 | `mvn test` |
| 通过 / 失败 | 118 通过 / 2 失败 |
| 已知失败 | `QixinSyncTest#retryOnce`（既有问题，与本次无关） |
| 记录时间 | 2026-09-24 |

**判定规则：没有基线记录的失败，一律视为自己引入的。** 这是唯一可执行的口径，否则每次都会陷入「这本来就是这样吧」的争论。

## 三、反查调用方

改一个方法、字段、枚举、配置项之前，先找出谁在用它。

| 改动对象 | 反查方式 |
| --- | --- |
| 方法 / 函数 | 全局搜索方法名：`rg "methodName"` |
| 接口 / HTTP 路径 | `rg "/api/xxx"`，同时检查前端调用点 |
| DTO / 类型字段 | `rg "fieldName"`，重点看序列化与前端类型定义 |
| 数据库字段 | 检索 SQL、Mapper XML、实体类、报表脚本 |
| 枚举值 | 检索所有分支判断与前端映射表 |
| 配置项 | 检索配置文件、部署脚本、环境变量清单 |

要求：**反查结果写进设计稿的「改动清单」**，每条标注是「需要同步修改」还是「确认不受影响」。只写前者、不写后者的改动清单是不完整的。

## 四、改动分级

不是所有改动都要同等防护。分级决定验证强度：

| 级别 | 判断标准 | 额外要求 |
| --- | --- | --- |
| 局部 | 只改一个方法内部或一个页面，无对外暴露 | 常规测试 + 证据 |
| 模块 | 改变模块内的公开方法或数据结构 | 反查调用方 + 模块级回归 |
| 公共 | 改公共模块、工具类、基础组件、全局配置 | 反查调用方 + 全量回归 + 双人评审 |
| 契约 | 改接口协议、错误码、分页结构、数据表结构 | 上述全部 + 契约文档同步 + 兼容方案 |

**拿不准时往上靠一级。** 少做防护的代价，远大于多做一次回归。

## 五、回归验证

验证阶段除了验证新功能，必须回归既有功能：

| 回归范围 | 怎么选 |
| --- | --- |
| 同一模块的其他功能 | 该模块相关测试全跑 |
| 直接调用方 | 反查出的调用点逐个验证 |
| 共享基础设施 | 改动涉及公共组件时跑全量测试 |
| 高频主流程 | 无论改什么，登录、列表、详情这类主流程至少手工过一遍 |

证据要求：

- 回归结果与**基线对比**，说明哪些失败是新增的、哪些是既有的。
- 在 `docs/verification/<主题>/验收报告.md` 中作为独立小节「回归验证」记录。
- 回归覆盖范围与未覆盖范围都要写，不能只写通过项。

## 六、自动化能覆盖到哪

| 覆盖得住 | 覆盖不住 |
| --- | --- |
| 函数契约、边界、异常路径 | 业务语义是否仍然正确 |
| 编译与类型错误 | UI 布局与交互细节 |
| 接口结构一致性 | 上下游系统的实际兼容性 |
| 已写过测试的既有行为 | 没写过测试的既有行为 |

**自动化测试是必要条件，不是充分条件。** 反查调用方与手工回归不可省略。

## 七、AI 参与时的注意事项

1. **先让它列调用方清单，再改代码。** 顺序颠倒会得到「改完了才发现还有 8 个调用点没跟上」。
2. **让它输出调用点表格**（文件、行号、是否需要同步改），而不是一句「已确认无影响」。
3. **不要拿「测试是绿的」当结论。** 要问：测的是哪几条路径？调用方覆盖了吗？
4. **公共方法的改动要求它给出所有调用点**，缺一个就是阻断项。
5. 回归失败时，先让它判断「这个失败在基线里存在吗」，再决定是否改代码。

## 八、反模式

| 反模式 | 问题 |
| --- | --- |
| 不记录基线就开始改 | 分不清既有失败与新增失败，责任无法界定 |
| 只写「已确认无影响」 | 无证据的结论，评审无法核对 |
| 改公共方法不查调用方 | 影响面靠运气 |
| 只跑新功能的测试 | 调用方既有功能静默失效 |
| 回归结论只写通过项 | 未覆盖范围被隐藏，评审误判风险 |
| 用「覆盖率没降」代替回归 | 覆盖率不反映业务语义是否仍正确 |
| 拿不准级别时往下靠 | 省一次回归，赔一次线上事故 |
