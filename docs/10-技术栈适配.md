# 技术栈适配

本模板的流程与语言无关，但**门禁命令**和**规范细节**必须落到具体技术栈。本文说明适配方式。

## 一、适配的三个要素

接入一个技术栈，只需要补齐三件事：

| 要素 | 位置 | 说明 |
| --- | --- | --- |
| 规范文档 | `docs/` 或项目自身文档 | 命名、分层、缩进、类型约定等 |
| 校验命令 | `package.json` / `pom.xml` / `Makefile` | 一个命令跑完该栈的全部检查 |
| 技能（可选） | `skills/` | 该栈的高频重复动作 |

不需要为每个技术栈写一套新的流程文档，流程只此一份。

## 二、内置适配

| 技术栈 | 校验命令 | 规范文档位置 |
| --- | --- | --- |
| Java / Spring Boot | `mvn test` | 项目内 `SPRING_GUIDELINES.md` 之类 |
| Vue 3 / Vite 管理后台 | `npm run validate` | 项目内 `ADMIN_GUIDELINES.md` 之类 |
| uni-app / Vue 3 移动端 | `npm run validate` | 项目内 `UNIAPP_GUIDELINES.md` 之类 |
| Node 脚本 / 工具 | `node scripts/check-docs.mjs` | 本仓库 `docs/` |

## 三、统一校验入口

无论几套技术栈，**对外只暴露一个命令**。约定：

```json
{
  "scripts": {
    "validate": "npm run validate:docs && npm run validate:web && npm run validate:server",
    "validate:docs": "node scripts/check-docs.mjs",
    "validate:web": "npm --prefix web run validate",
    "validate:server": "mvn -f server/pom.xml test -q"
  }
}
```

这样 Git 钩子与流水线只需调用 `npm run validate`，新增技术栈时不用改钩子。

若项目没有 Node 环境，可用 `Makefile` 作为统一入口：

```makefile
.PHONY: validate
validate: validate-docs validate-server

validate-docs:
	node scripts/check-docs.mjs

validate-server:
	cd server && mvn test -q
```

## 四、新增一个技术栈（示例：Python / FastAPI）

1. **写规范文档**，放在项目 `docs/` 下，例如 `docs/PYTHON_GUIDELINES.md`：
   - 目录分层（router / service / repository / model）
   - 类型注解与校验（Pydantic）
   - 错误码与统一响应外壳
   - 测试命名与结构（`tests/test_*.py`，覆盖正常 / 边界 / 异常）

2. **定义校验命令**，写进 `pyproject.toml` 或 `Makefile`：

```makefile
validate-py:
	ruff check .
	mypy .
	pytest -q
```

3. **接入统一入口**：把 `validate-py` 加进 `validate` 目标。

4. **更新 `AGENTS.md` 的阅读顺序表**，让 AI 在处理该栈代码时能读到规范文档。

5. **可选：写一个技能**。当某个动作每周重复 3 次以上时（例如「新增一个 CRUD 模块」），把它写成 `skills/<name>/SKILL.md`。

## 五、校验命令设计原则

| 原则 | 说明 | 反例 |
| --- | --- | --- |
| 快 | 本地钩子里的检查应在 60 秒内跑完 | 每次提交跑全量端到端测试 |
| 确定性 | 同样输入必然同样输出 | 依赖外部服务可用性 |
| 中文可读 | 输出能被人直接看懂 | 只报错误码不解释 |
| 可定位 | 报错必须带文件与行号 | 只输出「校验失败」 |

提交前与推送前的分工建议：

| 时机 | 跑什么 |
| --- | --- |
| `pre-commit` | 格式化、lint、类型检查、受影响模块的单元测试 |
| `pre-push` | 完整构建、跨模块测试 |
| 流水线 | 全量测试 + 文档检查 + 证据目录检查 |

## 六、多模块仓库的检查分发

`pre-commit` 钩子应**只检查本次改动的模块**，否则改一行文档却要跑全量，很快就会被绕过。

实现方式：按改动路径匹配后分发到对应命令。参考 `.githooks/pre-commit` 中的 `has_change` 模式：

```bash
if has_change '^web/'; then
  (cd "$ROOT/web" && npm run validate)
fi

if has_change '^server/'; then
  (cd "$ROOT/server" && mvn test -q)
fi
```

## 七、不适配也要遵守的部分

无论技术栈如何，以下内容不做适配，全项目统一：

- 六阶段流水线与门禁
- 提交信息格式与分支命名
- 文档职责边界（`AGENTS.md` / `SPEC.md` / `MEMORY.md` / `docs/` / `spec/`）
- 证据留档目录规范
- 密钥零入库
