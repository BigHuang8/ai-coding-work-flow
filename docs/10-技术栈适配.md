# 技术栈适配

本模板的流程与语言无关，但**门禁命令**和**规范细节**必须落到具体技术栈。本文回答两件事：

1. 一个已有项目怎么**无缝接入**——不覆盖既有约定，只补缺的。
2. 技术栈对不上时怎么办——**项目有、模板没有**，以及**模板有、项目没有**，两个方向都要有出口。

> 配图见 [`assets/stack-fit.png`](../assets/stack-fit.png)（三类清单）与 [`assets/gap-process.png`](../assets/gap-process.png)（缺口补规范五步）。

## 一、能力位：先把「缺什么」说清楚

不按「项目名」或「语言」比，按**能力位**比。一个能力位可以有多个实现，规范按能力位装配：

| 能力位 | 含义 | 模板当前覆盖 |
| --- | --- | --- |
| `server` | 后端服务 | Java / Spring Boot / Spring Cloud |
| `web` | Web 前端 | Vue 3 / Vite |
| `mobile` | 移动端 | uni-app / Vue 3 |
| `data` | 数据库与存储 | MySQL 8 表结构与迁移 |
| `tooling` | 脚本与工程工具 | Node 脚本（所有项目必装，`always`） |

登记表在 [stacks/registry.json](../stacks/registry.json)，字段说明与维护方式见 [技术栈登记表说明](../stacks/README.md)。探测结果永远是三类之一：

| 分类 | 含义 | 处理 |
| --- | --- | --- |
| 已启用 | 项目用到、模板有规范 | 规范进阅读顺序，校验命令进 `npm run validate` |
| 装箱未启用 | 模板有规范、项目没用到 | 不注入、不进阅读顺序、不进 CI，规范留在仓库备用 |
| 缺口 | 项目用到、模板没规范 | 走第三节的补规范流程，登记为 `provisional` |

## 二、无缝接入：只补不改

接入的默认行为是**只补不改**：已存在的文件一律跳过，冲掉项目既有约定比不接入更糟。

```bash
# 1. 先看会写什么、会动到什么，不落盘
node scripts/bootstrap.mjs --target ../your-project --dry-run

# 2. 正式注入：默认自动探测技术栈
node scripts/bootstrap.mjs --target ../your-project

# 3. 自检：登记表结构、已启用栈的规范是否到位、缺口是否认领
node scripts/detect-stack.mjs --check
```

注入完成后会生成两份项目侧文件：

- `workflow.config.json`：已启用栈、装箱栈、缺口、推荐校验命令，供任务看板与脚本消费。
- `docs/TECH_STACK.md`：人读的登记与接入记录，第三节的缺口必须有人认领并填上负责人与期限。

### 已有约定怎么融合

`bootstrap` 会自动体检，把「项目里已经有、不能覆盖」的项列成融合清单，写进 `docs/TECH_STACK.md` 第五节。规则如下：

| 已有的东西 | 处理方式 |
| --- | --- |
| 自有的 `CLAUDE.md` / `.cursorrules` / `.windsurfrules` | 不覆盖：把内容并入 `AGENTS.md`，再由 `node scripts/sync-agent-config.mjs` 重新生成入口 |
| 已有 CI（`.gitlab-ci.yml` / `Jenkinsfile` / 已有的 `.github/workflows/*` / Gitee Go 的 `.workflow/`） | 在现有流水线里**追加**校验步骤，不要另建第二套 |
| 已有钩子框架（`.husky` / `.pre-commit-config.yaml` / `lefthook.yml`） | 二选一：用模板的 `.githooks`，或在既有框架里调用同样命令；两套并存必然互相绕过 |
| 已有 `package.json` 的 `validate` | 把模板的检查项（`check-docs`、`check-skills`、`detect-stack`、`sync-agent-config`、`sync-platform`）**合并**进去，不要覆盖原有内容 |

生成型文件（`CLAUDE.md`、`.cursor/rules/00-workflow.mdc`、`.github/copilot-instructions.md`）带生成标记；同步脚本遇到没有标记的同名文件会**跳过并提示**，不会静默覆盖。确认要丢弃时显式加 `--force`。
用不到的入口在 `workflow.config.json` 的 `aiEntries` 里去掉即可，脚本不再生成对应文件（例如不用 Copilot 就没有 `.github/`）。

### 无缝接入的验收标准

- [ ] `npm run validate` 通过
- [ ] `node scripts/detect-stack.mjs --check` 通过（缺口在严格模式下会被拦住，见第四节）
- [ ] `docs/TECH_STACK.md` 的三类清单与实际一致，缺口有负责人与期限
- [ ] 融合清单里的每一项都已处理，或明确决定不处理并写明原因
- [ ] 项目原有 CI 仍然通过，没有被本模板的检查顶掉

## 三、项目有、模板没有：补规范

**触发**：`node scripts/detect-stack.mjs` 报告缺口，例如项目用 React 而模板只有 Vue 3 规范。

**红线**：缺口存在时，AI 不得凭通用最佳实践自由发挥。先把约定定下来，再写代码。

五步流程：

1. **认领**：在 `docs/TECH_STACK.md` 第三节填负责人与期限。没人认领的缺口，等于这个项目没接入。
2. **写最小规范**：在项目 `docs/` 下新建例如 `docs/REACT_GUIDELINES.md`，只写四要素，不追求一次写全。
3. **登记为临时**：在项目 `stacks/registry.json` 的 `stacks[]` 追加一条 `status: "provisional"`，填 `guidelines` 与 `validate`。
4. **接入门禁**：把该栈的校验命令并进 `npm run validate`，并把规范路径写进项目 `AGENTS.md` 的阅读顺序表。
5. **限期转正**：一个月内补齐到 `built-in` 水平并转正，长期停在 `provisional` 会被 `detect-stack --check` 持续提示。

### 最小规范的四个要素

只写这四块，每块三到十条，够用即可：

| 要素 | 说明 | 反例 |
| --- | --- | --- |
| 分层与依赖方向 | 代码放哪层、谁能调谁 | 「按情况组织代码」 |
| 命名与类型约定 | 文件、符号、类型、错误处理方式 | 「命名要规范」 |
| 错误与响应外壳 | 统一返回结构、错误码、日志边界 | 不写，各自发挥 |
| 测试要求 | 测试放哪、命名、必覆盖的路径 | 「要有测试」 |

骨架示例（项目侧 `docs/REACT_GUIDELINES.md`）：

```markdown
# React 开发规范（provisional）

## 一、分层与依赖方向
- 页面在 `src/pages/`，复用组件在 `src/components/`，数据请求集中在 `src/api/`。
- 组件不得直接拼接请求 URL，一律走 `src/api/` 导出的函数。

## 二、命名与类型
- 组件文件 PascalCase，hook 以 `use` 开头，类型定义集中在 `src/types/`。
- 禁止 `any`；第三方库缺少类型时补齐本地声明。

## 三、错误与响应
- 统一走 `src/api/client.ts` 的响应外壳，错误码集中定义，不在页面里硬编码字符串。

## 四、测试
- 关键交互用 `*.test.tsx`，覆盖正常、边界、异常三条路径。
```

转正标准：规范里能回答「新人照着写不会跑偏」；`validate` 命令能在 60 秒内跑完；连续两个需求没有再因为该栈的约定不明确而产生返工。

## 四、模板有、项目没有：装箱不启用

模板里写好的 Vue 3、uni-app、MySQL 规范，在一套纯后端 Java 服务里确实用不到。处理方式是**装箱**，不是删除：

- **不注入阅读顺序**：项目 `AGENTS.md` 的阅读顺序表只列已启用的栈。
- **不进 CI**：`workflow.config.json` 的 `stacks` 只写已启用栈，`availableStacks` 记录装箱项，校验命令不会被聚合进来。
- **文档留在仓库里**：规范文件仍在 `docs/`，标为装箱项。团队换项目、加模块时直接启用，不用从头再写一遍。

为什么不做物理删除：规范是团队的资产，一份 Vue 3 规范可以同时喂给三个项目；删掉只会让下一个项目重新踩同样的坑。

需要显式表达「这个项目永久不会用到某栈」时，在项目 `AGENTS.md` 里写一句结论即可（例如「本项目为纯后端服务，前端规范不适用」），规范文档照旧留着。

## 五、校验入口与适配三要素

接入一个技术栈只需要补齐三件事：

| 要素 | 位置 | 说明 |
| --- | --- | --- |
| 规范文档 | 模板 `docs/` 或项目 `docs/` | 命名、分层、类型、错误处理等约定 |
| 校验命令 | `package.json` / `pom.xml` / `Makefile` | 一个命令跑完该栈的全部检查 |
| 探测规则 | `stacks/registry.json` | 让脚本能认出项目用了这个栈 |

内置适配：

| 技术栈 | registry id | 校验命令 | 规范文档 |
| --- | --- | --- | --- |
| Java / Spring Boot / Spring Cloud | `java-springboot` | `mvn test -q` | [13-后端规范-Java-Spring](13-后端规范-Java-Spring.md) |
| Vue 3 / Vite 管理后台 | `vue3-web` | `npm run validate` | [14-前端规范-Vue3](14-前端规范-Vue3.md) |
| uni-app / Vue 3 移动端 | `uniapp-vue3` | `npm run validate` | [14-前端规范-Vue3](14-前端规范-Vue3.md) |
| MySQL 8 表结构与迁移 | `mysql-schema` | 人工评审清单 | [15-数据库设计与建表规范](15-数据库设计与建表规范.md) |
| Node 脚本与工具 | `node-tooling` | `node scripts/check-docs.mjs` | [05-分支提交与评审](05-分支提交与评审.md) |

约定顺序：**模板规范兜底 → 项目规范细化**。项目规范只写「模板没写、或与模板不同」的部分，禁止整篇复制模板内容；否则同一件事会有两处说法，早晚不一致。

探测规则写在 `stacks/registry.json` 的 `detect` 字段里，四种证据可以组合：

| 字段 | 证据形态 | 用在哪 |
| --- | --- | --- |
| `files` | 文件或目录路径，支持 `**/*.ext` 与 `**/name` | 构建文件、框架特征文件（`go.mod`、`pages.json`） |
| `packageDeps` | `package.json` 里的依赖名 | 前端与 Node 生态 |
| `pomKeywords` | `pom.xml` / Gradle 构建文件里的关键字 | JVM 生态 |
| `sqlKeywords` | `.sql` 文件内容里的方言关键字 | 数据库方言（MySQL 的 `auto_increment`、PostgreSQL 的 `bigserial`） |

写探测规则的三条经验：

1. **按证据判定，不按扩展名猜**：早期规则用 `**/*.sql` 判定 MySQL，结果 PostgreSQL 项目也被算成 MySQL；
   改成方言关键字后才判得准——一个项目用错规范，比探测不到更糟；
2. **模板自己注入的文件不算证据**：`db/` 是模板会创建的目录，不能拿它当「项目在用某数据库」的依据；
3. **探测不到就显式指定**：`--stack java-springboot,vue3` 比放宽规则安全。

统一校验入口：无论几套技术栈，对外只暴露一个命令，新增栈时不用改钩子与流水线。

```json
{
  "scripts": {
    "validate": "npm run validate:docs && npm run validate:skills && npm run validate:stacks && npm run validate:web && npm run validate:server",
    "validate:docs": "node scripts/check-docs.mjs",
    "validate:skills": "node scripts/check-skills.mjs",
    "validate:stacks": "node scripts/detect-stack.mjs --check",
    "validate:agents": "node scripts/sync-agent-config.mjs --check",
    "validate:platform": "node scripts/sync-platform.mjs --check",
    "validate:web": "npm --prefix web run validate",
    "validate:server": "mvn -f server/pom.xml test -q"
  }
}
```

没有 Node 环境的项目，用 `Makefile` 做统一入口（`make validate` 调用同样的命令）。

### 严格模式什么时候打开

`detect-stack.mjs --check` 默认把缺口当**警告**（退出码 0），适合刚接入、还没补规范的阶段：

- 接入期：`node scripts/detect-stack.mjs --check`，缺口提示但不拦人。
- 稳定期：`node scripts/detect-stack.mjs --check --strict`，缺口直接失败，写进流水线。

建议接入满一个月后切严格模式。切换时同步更新项目 `README` 或 `AGENTS.md` 的命令索引，避免有人不知道门禁变严。

## 六、新增一个技术栈（模板侧，示例：Python / FastAPI）

1. **写规范文档**：`docs/16-后端规范-Python-FastAPI.md`，按第三节的四要素组织：
   - 分层（router / service / repository / model）与依赖方向
   - 类型注解与校验（Pydantic）
   - 错误码与统一响应外壳
   - 测试命名与结构（`tests/test_*.py`，正常 / 边界 / 异常）
2. **登记**：在 [stacks/registry.json](../stacks/registry.json) 的 `stacks[]` 追加一条，填 `guidelines`、`validate` 与探测规则。
3. **定义校验命令**：`ruff check . && mypy . && pytest -q`，并接入项目的统一入口。
4. **自检**：`node scripts/detect-stack.mjs --check`，确认登记表结构合法、规范路径存在。
5. **可选：写一个技能**。当某个动作每周重复 3 次以上（例如「新增一个 CRUD 模块」），把它写成 `skills/<name>/SKILL.md`。

## 七、校验命令设计原则

| 原则 | 说明 | 反例 |
| --- | --- | --- |
| 快 | 本地钩子里的检查应在 60 秒内跑完 | 每次提交跑全量端到端测试 |
| 确定性 | 同样输入必然同样输出 | 依赖外部服务可用性 |
| 中文可读 | 输出能被人直接看懂 | 只报错误码不解释 |
| 可定位 | 报错必须带文件与行号 | 只输出「校验失败」 |

提交前与推送前的分工建议：

| 时机 | 跑什么 |
| --- | --- |
| `pre-commit` | 格式化、lint、类型检查、受影响模块的单元测试 |
| `pre-push` | 完整构建、跨模块测试 |
| 流水线 | 全量测试 + 文档检查 + 技术栈自检 + 证据目录检查 |

## 八、多模块仓库的检查分发

`pre-commit` 钩子应**只检查本次改动的模块**，否则改一行文档却要跑全量，很快就会被绕过。

实现方式：按改动路径匹配后分发到对应命令。参考 `.githooks/pre-commit` 中的 `has_change` 模式：

```bash
if has_change '^web/'; then
  (cd "$ROOT/web" && npm run validate)
fi

if has_change '^server/'; then
  (cd "$ROOT/server" && mvn test -q)
fi
```

## 九、不适配也要遵守的部分

无论技术栈如何，以下内容不做适配，全项目统一：

- 六阶段流水线与门禁
- 提交信息格式与分支命名
- 文档职责边界（`AGENTS.md` / `SPEC.md` / `MEMORY.md` / `docs/` / `spec/`）
- 证据留档目录规范
- 密钥零入库
- 只使用仓库内技能
