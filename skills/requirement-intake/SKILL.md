# 需求接收与拆解

把外部交付的需求材料，转成可验收、可追溯、带技术实现标注的内部需求条目。

流程说明见 `docs/11-需求接收与拆解.md`。本文是该流程的可执行版本。

## 何时使用

- 收到 PRD、原型图、需求文档、需求截图，需要开始一个任务。
- 需求材料只有自然语言段落，缺少验收标准与实现路径。
- 需要把「产品要什么」翻译成「改哪些文件、怎么改」。

## 何时不要使用

- 需求只是口头一句话，没有正式交付物 → 用 `spec-writer`，不要拉长流程。
- 需求已在 `SPEC.md` 中完整定义，只是要动手实现 → 走 ② 方案设计。

## 输入

需要向使用者确认（缺失就问）：

1. **材料位置**：PRD 文件、原型文件/链接的原始路径。
2. **交付人**：谁给的，遇到歧义找谁。
3. **期限与优先级**：影响裁剪程度。
4. **已知约束**：不能改的接口、必须兼容的老版本、上线窗口。

## 步骤

### 1. 建档并归档原件

```bash
node scripts/new-spec.mjs --title "<主题>" --with-artifacts --with-verification
```

- PRD 原件放入 `spec/<日期>-<主题>/原始需求/`
- 原型件放入 `spec/<日期>-<主题>/原型/`
- **保留原始文件名**；原型截图用页面名命名，如 `客户列表-默认.png`
- 在「原件清单」登记每个原件：类型、版本 / 日期、存放位置

**不要修改原件。** 新版原件另存并追加清单行，不覆盖旧版。

### 2. 补 markdown 转换件

`.docx`、`.pdf` 里的内容 AI 检索不到。在原件旁生成同名 `.md` 转换件：

- 保留原文结构与措辞，**只做格式转换，不做改写**
- 在转换件顶部标注：`> 本文件为「<原名>」的转换件，内容冲突时以原件为准`

### 3. 需求编号

给每条需求一个 `R1`、`R2`…… 编号，并标注出处（PRD 第几节 / 原型第几页）。

**编号是追溯链的关键**：设计稿、提交信息、评审结论、验收报告都引用同一个编号。

### 4. 逐条写验收标准

对每条需求，写可判定的验收条件：

| 不合格写法 | 合格写法 |
| --- | --- |
| 「体验要友好」 | 无数据时展示文案「暂无符合条件的客户」 |
| 「筛选要快」 | 1000 条数据下筛选响应 < 800ms |
| 「要支持多选」 | 选中 A、B 两个团队时，结果为两团队客户并集；不选等于全部 |

同时写清**范围外**：这条需求明确不做什么。

### 5. 填技术实现对照

**这一步是「在需求文档里加技术实现」的落地方式**，技术内容一律写进对照表，不写回 PRD。

| 编号 | 技术实现要点 | 影响文件 / 接口 | 已有基础 | 预估工作量 | 风险 |
| --- | --- | --- | --- | --- | --- |

要求：

- 技术实现要点说清「改哪一层、用什么机制」——**写方案，不写代码**。
- 影响文件精确到文件或接口；接口变更必须同时标注「需同步 `docs/API_CONTRACT.md`」。
- **先查已有基础**：读相关代码，确认能否复用现有实现。不要凭想象设计。
- 风险栏不许留空：确实无风险就写「无」。

### 6. 整理待确认项

把材料里没讲清、或自相矛盾的地方列出来，写明由谁确认：

| # | 问题 | 由谁确认 | 状态 |
| --- | --- | --- | --- |

**不允许用猜测填空。** 猜出来的需求会被写进 `SPEC.md`，后面返工代价最高。

### 7. 提炼进 SPEC.md 并交接

- 把稳定的需求与验收标准写进 `SPEC.md`，并反向链接 `spec/<日期>-<主题>/`
- 输出交接说明：进入 ② 方案设计，设计稿需逐条回应技术对照表里的风险

## 输出

1. `spec/<日期>-<主题>/需求与技术对照.md`（来源、原件清单、需求条目、技术对照、待确认项）
2. 原件归档：`原始需求/`、`原型/`（含 markdown 转换件）
3. `SPEC.md` 对应条目（含反向链接）
4. 一份待确认项清单，标明确认人与影响

## 质量门禁

- [ ] 原件已归档且未被修改，清单里登记了版本与日期
- [ ] 二进制原件旁有 markdown 转换件，并声明「以原件为准」
- [ ] 每条需求都有 `R` 编号与出处
- [ ] 每条验收标准可判定，无「友好 / 流畅 / 合理」这类词
- [ ] 范围外已明确写出
- [ ] 技术对照表逐条填写，影响文件到文件级，风险栏无空缺
- [ ] 待确认项写明了确认人，没有用假设填空
- [ ] `SPEC.md` 已更新并反向链接到需求目录

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 把技术实现直接写进 PRD 原件 | 污染外部交付物，且无法回溯版本 |
| 原件放在 `docs/` 根目录 | 无法追溯是哪次需求、哪一版 |
| 收到新版覆盖旧版 | 丢失历史，无法解释需求演变 |
| 只存 `.docx` 不转换 | AI 检索不到，每次都要人工转述 |
| 技术对照只写「改一下查询」 | 无法评估影响面，评审无法核对 |
| 跳过「已有基础」一栏 | 容易重复实现已有能力 |
| 待确认项凭经验补全 | 错误固化，返工成本最高 |
| 原型差异不记录 | 上线后才发现与原型不符 |
