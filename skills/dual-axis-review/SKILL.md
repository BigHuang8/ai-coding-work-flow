# 双轴评审

沿两条轴评审同一次变更，避免「只看了风格没看需求」或「只看了功能没看规范」。

- **规范轴**：代码是否遵守团队约定（`docs/`、`AGENTS.md`、技术栈规范）。
- **需求轴**：变更是否真的实现了 `SPEC.md` 中承诺的验收标准。

两轴必须独立进行。先做完一轴再开始另一轴，避免互相影响判断。

## 何时使用

- 合并前的代码评审。
- 作者自审（自审用于发现问题，不能替代他人评审）。
- 需要确认「改动是否超出了需求范围」。

## 何时不要使用

- 纯文档改动且不涉及规范变更（用 `node scripts/check-docs.mjs` 即可）。
- 变更范围极小且无逻辑改动（如改文案）。

## 输入

1. **变更范围**：分支名、提交范围或 PR。
2. **需求依据**：`SPEC.md` 对应条目、`spec/` 文件、验收标准。
3. **验证证据**：`docs/verification/` 下的证据目录（没有则直接判定为「未验证」）。

先确认变更范围与需求依据，缺需求依据时要求补齐，不要靠猜。

## 步骤

### 准备

```bash
# 变更文件清单
git diff --name-only <base>...<head>

# 详细差异
git diff <base>...<head>
```

先确认三件事：

1. 变更文件是否都在需求范围内？（有越界文件直接记为阻断项）
2. 是否有测试文件？（没有则记为阻断项，除非裁剪规则允许）
3. 是否有证据目录？（没有则记为阻断项）

### 规范轴

逐条核对，**每条都要给出结论或「不适用」**：

- [ ] 提交信息符合 `type(scope): subject` 格式
- [ ] 分支命名符合 `<type>/<short-desc>`
- [ ] 校验命令通过（`npm run validate` / `mvn test` 等）
- [ ] 未修改与任务无关的文件
- [ ] 无新增静默抑制（`@ts-ignore`、`# noqa`、注释掉的测试、放宽的 lint 规则）
- [ ] 无密钥、口令、真实用户数据进入改动
- [ ] 接口变更已同步 `docs/API_CONTRACT.md` 与两端类型定义
- [ ] 列表接口符合分页与错误码约定
- [ ] 文档已同步（`SPEC.md` / `MEMORY.md` / `docs/` 至少一处）
- [ ] 符合技术栈规范（分层、命名、缩进、类型使用）

### 需求轴

- [ ] 逐条列出验收标准并标注是否满足，**不允许合并成一句「功能已实现」**
- [ ] 范围外的事确实没做
- [ ] 边界与异常路径有处理：空值、越界、超限、并发、无权限
- [ ] 测试能体现验收标准（不是只测了 happy path）
- [ ] 证据可复现：评审者本人按文档能跑出同样结果
- [ ] 未覆盖项已被明确说明

### 输出结论

```text
结论：需整改

规范轴：
- 阻断：CustomerQueryRequest.java:23 新增参数未加校验注解 @NotNull
- 阻断：docs/API_CONTRACT.md 未同步团队筛选参数
- 通过：提交信息、分支命名、无越界文件、无密钥
- 不适用：分页约定（本次未改分页）

需求轴：
- 阻断：验收标准 3「空结果展示空态文案」未实现
- 通过：验收标准 1、2、4
- 未覆盖：> 1000 条数据的筛选性能

整改建议（按优先级）：
1. 补 @NotNull 与契约文档
2. 补空态文案
3. 补充边界测试（空数组、全部取消选择）
```

## 输出

结构化评审结论，包含：结论（通过 / 需整改）、两轴各自的阻断项与通过项、未覆盖项、整改清单。

## 质量门禁

- [ ] 两轴都做了，没有只做一轴
- [ ] 阻断项与建议项**分开列出**
- [ ] 每条问题都带**文件与行号**，可被直接定位
- [ ] 需求轴逐条对照验收标准，而不是笼统评价
- [ ] 没有出现「看起来还行」「应该没问题」这类无结论的表述
- [ ] 证据缺失时明确判定为「未验证」，而不是默认通过

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 只评审代码风格 | 需求做错了也发现不了 |
| 把建议项写成阻断项 | 拖慢交付，作者开始敷衍评审 |
| 把阻断项写成建议项 | 风险被带上线 |
| 「整体看起来不错，可以合并」 | 无信息量的结论，等于没评审 |
| 评审者直接改代码 | 职责混淆，作者失去了理解变更的机会 |
| 因为作者是资深成员就跳过需求轴 | 资历不改变需求是否被实现的客观事实 |
