# 流程编排

把六阶段流水线落到当前任务上，给出明确的下一步动作，避免「先动手再说」。

## 何时使用

- 接到一个新任务，不确定从哪开始。
- 任务进行到一半，不确定算不算完成。
- 想裁剪流程，需要判断能否裁剪、要补什么。

## 何时不要使用

- 任务已经明确定位在当前阶段，直接按 `docs/01-工作流总览.md` 执行即可。
- 纯咨询类问题，没有实际改动。

## 输入

需要向使用者确认（缺失就问，不要猜）：

1. **任务描述**：要做什么。
2. **已知信息**：需求文档、原型、issue、相关代码位置。
3. **当前状态**：已经做了什么，卡在哪里。
4. **改动规模**：涉及几个模块、是否改接口、是否动数据库。

## 步骤

### 1. 判定阶段

按下表定位当前阶段。拿不准时按「更靠前」的阶段处理。

| 现象 | 当前阶段 |
| --- | --- |
| 需求只有口头描述，说不清验收标准 | ① 需求澄清 |
| 需求清楚了，但不知道改哪些文件 | ② 方案设计 |
| 清楚改什么，还没写代码 | ③ 实现 |
| 代码写完，没有跑过验证 | ④ 验证 |
| 有证据，还没人看过 | ⑤ 评审 |
| 评审通过，还没合并或没写回滚方式 | ⑥ 交付 |

### 2. 判断是否可裁剪

对照 `docs/01-工作流总览.md` 第三节的裁剪规则：

- 文案 / 样式微调 → 可跳过 ①②⑤
- 单文件 Bug 修复 → 可跳过 ②
- 线上紧急修复 → 可跳过 ①②，事后 3 个工作日补记录
- 新增接口 / 新功能 / 跨模块重构 → 不可裁剪

裁剪必须显式声明：`本次裁剪：跳过②，理由：<...>`。

### 3. 给出下一步

输出格式：

```text
当前阶段：② 方案设计
进入该阶段的判据：需求已在 SPEC.md#客户管理 确认，验收标准 4 条已定

下一步动作：
1. 列出改动文件清单（含新增文件）
2. 写清接口变化与是否兼容
3. 写明回滚方式
产出：docs/designs/<日期>-<主题>-设计.md

本阶段门禁：改动清单、影响面、回滚方式三者齐全。缺任一项不得开工。

需要你确认：<需要使用者决策的问题，若无需决策则写「无」>
```

### 4. 主动提示风险

在输出末尾补充该阶段最常见的失败模式，例如：

- ① 阶段：验收标准不可判定（出现「体验好」「速度快」这类词）。
- ② 阶段：漏掉数据迁移与回滚。
- ③ 阶段：顺手改了无关文件。
- ④ 阶段：只留结论不留命令与输出。
- ⑤ 阶段：把建议项与阻断项混在一起。
- ⑥ 阶段：没写回滚方式。

## 输出

一份定位结论 + 下一步动作清单 + 需确认事项。可直接作为回复发给使用者。

## 质量门禁

- [ ] 明确说了当前阶段，且给出了判定依据
- [ ] 下一步动作是**可执行**的（能直接开始做，不是「设计方案」这类空话）
- [ ] 写明了该阶段的门禁内容
- [ ] 如涉及裁剪，显式说明了裁剪项与理由
- [ ] 不确定的信息标注为待确认，并写明由谁确认

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 直接开始写代码，不给阶段定位 | 该澄清的没澄清，后期返工 |
| 给出「建议先设计一下」这类空泛建议 | 使用者无法执行 |
| 帮使用者决定验收标准 | 越权，验收标准需需求方确认 |
| 默认流程全量执行 | 小改动也被流程拖死，导致团队抵触流程 |
| 只说阶段不说门禁 | 使用者不知道做到什么程度算完成 |
