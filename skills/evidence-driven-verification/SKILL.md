# 证据驱动的验证

在说「完成 / 修好 / 通过」之前，产出可被他人复现的证据，并落盘到 `docs/verification/`。

## 核心原则

**先说要跑什么、预期是什么，再跑，再原样记录结果。** 顺序颠倒就会出现「先有结论，再补证据」。

## 何时使用

- 实现完成后、评审之前（对应流水线第 ④ 阶段）。
- 修复线上问题时确认修复生效。
- 交付前需要向非开发者证明功能可用。

## 何时不要使用

- 纯文档改动（用链接检查与渲染预览即可）。
- 尚未实现完成（应先回到 ③ 阶段）。

## 输入

1. **验收标准**：来自 `SPEC.md` 或 `spec/` 文件。缺失时先补，不要凭感觉验证。
2. **变更范围**：改了哪些文件、哪些接口（用于确定验证面）。
3. **环境信息**：在哪个环境验证、依赖哪些服务、什么数据前提。

## 步骤

### 1. 列出验证计划

在动手前先输出以下内容并确认：

```text
验证计划
范围：<模块 / 接口 / 页面>
环境：<本地 / 测试环境；服务端口>
数据前提：<例如「一组」12 名客户；「二组」0 名客户>

用例：
1. 正常路径：<操作> → 预期 <结果>
2. 边界：<例如不选任何团队> → 预期 <全部>
3. 异常：<例如传入不存在的团队 ID（已删除）> → 预期 <空列表，不报错>

将执行的命令：
- <命令 1>
- <命令 2>
```

**先把预期写出来。** 预期写错的当场就能发现理解偏差，这是最便宜的纠错时机。

### 2. 执行并记录

规则：

- **命令与输出一起记录**，不要只记输出。
- 输出**原样保留**，包括失败与警告。失败也是证据，且往往更有价值。
- 敏感信息脱敏为 `***`，不要因为「方便」把 Token 贴进证据。
- 记录时间与环境，让结果可定位。

### 3. 覆盖三类路径

至少各一条：

| 类型 | 说明 | 例 |
| --- | --- | --- |
| 正常 | 预期的主要用法 | 选中两个团队，结果包含两个团队的客户 |
| 边界 | 空值、全部、极值、上限 | 不选团队 = 全部；选 0 条数据的团队 = 空态 |
| 异常 | 非法输入、无权限、超时、依赖失败 | 传入已删除的团队 ID 应返回空列表且不报错 |

**只验证正常路径是最常见的漏验证模式。**

### 4. 落盘

```text
docs/verification/<YYYYMMDD>-<主题>/
├── 验收报告.md
├── 命令记录.md
└── assets/
```

验收报告按 `docs/06-验收与证据留档.md` 第四节的模板撰写，逐条对照验收标准，并**明确列出未覆盖项**。

### 5. 给出结论

结论只有三种，不要模糊表述：

| 结论 | 含义 | 后续 |
| --- | --- | --- |
| 通过 | 全部验收标准满足，无未覆盖项 | 进入 ⑤ 评审 |
| 部分通过 | 部分满足，或有明确未覆盖项 | 说明缺口与影响，交评审判断 |
| 未通过 | 存在不满足的验收标准 | 回到 ③ 阶段，**不要先改代码再补结论** |

## 输出

1. `docs/verification/<日期>-<主题>/验收报告.md`
2. `docs/verification/<日期>-<主题>/命令记录.md`
3. `assets/` 下的截图等附件
4. 一段可直接粘贴到 PR 的结论摘要

## 质量门禁

- [ ] 验证前先写出了预期结果
- [ ] 命令与原始输出成对出现，未加工
- [ ] 覆盖正常、边界、异常三类路径
- [ ] 逐条对照验收标准，而不是笼统描述
- [ ] 明确写出了未覆盖项
- [ ] 换一个人按文档能复现出同样结果
- [ ] 无未脱敏的敏感信息

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 只汇报「验证通过」，不贴命令与输出 | 不可复现，等于没验证 |
| 先下结论再补证据 | 会不自觉地挑选有利结果 |
| 只测正常路径 | 边界与异常缺陷留到线上 |
| 验证失败后先改代码，再报告「通过」 | 掩盖了问题，错过了理解根因的机会 |
| 用本地结果代表测试 / 生产环境 | 环境差异导致的缺陷被漏掉 |
| 截图不带数据前提 | 无法判断是否覆盖了关键边界 |
| 为了好看而隐瞒未覆盖项 | 评审者误判风险，可能直接合并 |
