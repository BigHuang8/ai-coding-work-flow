# 需求澄清与建档

把模糊的需求变成可判定、可追溯、无歧义的需求条目，并留档到 `spec/`。

## 何时使用

- 需求来自口头描述、聊天记录、会议结论，没有正式交付物，需要固化。
- 需要写或补验收标准。
- 需求边界不清，需要明确「不做什么」。

## 何时不要使用

- 需求已经完整写在 `SPEC.md` 里，只是要改措辞。
- 收到了正式 PRD / 原型图 → 用 `requirement-intake`，它包含原件归档与技术实现对照。
- 纯技术任务（如升级依赖），没有业务验收标准。

## 输入

至少需要拿到以下之一：口头描述、聊天记录、原型、现有文档。**信息不足时先提问，不要脑补。**

必须追问到位的六件事：

1. **谁用**：这个功能的直接使用者是谁。
2. **什么场景**：在什么情况下会用到。
3. **要什么**：期望的行为是什么。
4. **不要什么**：明确的范围外。
5. **怎么算做完**：可判定的验收条件。
6. **边界与异常**：空数据、超限、无权限、重复操作时怎样。

## 步骤

### 1. 建档

```bash
node scripts/new-spec.mjs --title "<需求主题>"
```

生成 `spec/<YYYYMMDD>-<主题>/需求与技术对照.md` 后，填入「原始描述」「需求条目」「待确认项」。

**保留原始措辞，不要润色。** 润色会丢失原始意图。

### 2. 写验收标准

把描述转成可判定的条件。转换方法：

| 模糊描述 | 转成 |
| --- | --- |
| 「要快」 | 首屏渲染 < 1 秒（本地环境，100 条数据） |
| 「要能筛选」 | 支持按 A、B 筛选；A 可多选；不选等于全部 |
| 「要友好」 | 无数据时展示文案「暂无符合条件的记录」 |
| 「要兼容」 | 旧参数仍可用，行为与改造前一致 |
| 「要安全」 | 未登录访问返回 100401，且不泄漏数据内容 |

**红线：验收标准里不允许出现「友好」「流畅」「合理」「尽快」这类无法判定的词。**

### 3. 列出范围外

明确写出「本次不做什么」。这是减少返工最有效的一句话。

例如：「不支持按标签组合筛选（后续需求）」「不改造移动端（仅后台生效）」。

### 4. 标注待确认项

格式：`- <问题>（由 <角色> 确认）`。

无法确认的不要猜，标注清楚即可。**不要用假设的答案填充，那样会把错误固化进文档。**

### 5. 合并进 SPEC.md

把确认后的内容写进 `SPEC.md` 对应模块，并关联 `spec/` 文件：

```markdown
### 1.1 客户列表

- 需求：支持按团队、状态筛选，支持关键字搜索
- 验收标准：
  1. 团队筛选支持多选，不选等于全部
  2. 筛选结果为空时展示空态文案「暂无符合条件的客户」
  3. 列表默认每页 20 条，支持切换 50 / 100
- 范围外：不支持按标签组合筛选
- 关联：spec/20260924-客户列表团队筛选.md
```

## 输出

1. `spec/<日期>-<主题>/需求与技术对照.md` 需求主文档。
2. `SPEC.md` 中对应模块的条目。
3. 一份「待确认项清单」，写明由谁确认。

## 质量门禁

- [ ] 每条验收标准都是可判定的，不含模糊形容词
- [ ] 明确写了范围外
- [ ] 明确写了待确认项及确认人，没有用假设填空
- [ ] `spec/` 主文档中保留了原始描述
- [ ] `SPEC.md` 与 `spec/` 双向关联
- [ ] 找一个人复述需求，复述结果与文档一致

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 自行补充需求细节 | 固化错误假设，后期大规模返工 |
| 验收标准写成「功能正常」 | 无法判定，评审与验收都失去依据 |
| 只写要做什么，不写不做什么 | 范围无限膨胀 |
| 把技术方案写进需求 | 需求与设计混淆，方案变更时需求也要改 |
| 需求变更时新开一个文档 | 出现多份并存的需求，AI 随机读到一份 |
