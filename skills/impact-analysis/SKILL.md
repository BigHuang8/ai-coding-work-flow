# 影响面与回归防护

回答一个问题：**这次改动会不会弄坏已经跑通的功能？**

规范说明见 `docs/12-影响面与回归防护.md`。本文是可执行版本。

## 何时使用

- 要改公共模块、工具类、基础组件、全局配置。
- 要改接口协议、错误码、分页结构、数据库表结构。
- 要改一个不确定有多少调用方的方法或字段。
- 验证阶段需要证明「没有弄坏既有功能」。

## 何时不要使用

- 纯新增文件且无任何既有代码引用它。
- 只改文案、注释、样式且不影响逻辑。

## 输入

1. **改动对象**：具体文件、方法、字段、接口路径或配置项。
2. **技术栈**：决定用哪些反查手段。
3. **当前测试状态**：能不能跑、跑一次要多久。

## 步骤

### 1. 记录基线（改动之前做）

```bash
git status          # 必须干净，否则基线不可信
npm run validate    # 或 mvn test / pytest，按技术栈
```

输出：

| 项 | 基线结果 |
| --- | --- |
| 校验命令 |  |
| 通过 / 失败 |  |
| 已知失败项（与本次无关） |  |
| 记录时间 |  |

**没做基线的失败，一律视为本次引入。**

### 2. 反查调用方

逐项搜索，输出成表格：

| 调用点 | 位置 | 处理 |
| --- | --- | --- |
|  | 文件:行号 | 需同步修改 / 确认不受影响 |

搜索建议（按改动对象选择）：

```bash
# 方法名
rg "methodName" --type-not md

# 接口路径
rg "/api/xxx"

# 字段名（含序列化与前端类型）
rg "fieldName"

# 枚举值
rg "ENUM_VALUE"

# 配置键
rg "config.key"
```

要求：

- **每条都要给结论**，不能只列「需要改的」，也要列「确认不受影响的」。
- 前端与后端都要查：改后端字段要确认前端类型定义与页面映射。
- 数据库字段要查 SQL、Mapper XML、实体类、报表脚本四处。

### 3. 评定改动级别

| 级别 | 判断标准 | 额外要求 |
| --- | --- | --- |
| 局部 | 单方法内部或单页面，无对外暴露 | 常规测试 + 证据 |
| 模块 | 模块内公开方法或数据结构变化 | 反查调用方 + 模块级回归 |
| 公共 | 公共模块、工具类、基础组件、全局配置 | 反查调用方 + 全量回归 + 双人评审 |
| 契约 | 接口协议、错误码、分页结构、表结构 | 上述全部 + 契约文档同步 + 兼容方案 |

**拿不准时往上靠一级。**

### 4. 把影响面写进设计稿

改动清单要包含两部分：

- 需要同步修改的文件（含调用方）
- 确认不受影响的文件（说明为什么不受影响）

只写前者的改动清单是不完整的，评审无法判断你是否真的查过。

### 5. 回归验证

按级别选择回归范围，并**与基线对比**：

| 回归范围 | 何时必须做 |
| --- | --- |
| 模块相关测试 | 模块级及以上 |
| 反查出的调用点逐个验证 | 模块级及以上 |
| 全量测试 | 公共级及以上 |
| 主流程手工验证（登录、列表、详情） | 所有级别 |

回归结论作为独立小节写进 `docs/verification/<主题>/验收报告.md`：

```markdown
## 回归验证

- 基线：<命令>，<通过数> 通过 / <失败数> 失败
- 本次：<通过数> 通过 / <失败数> 失败
- 新增失败：无 / <列出>
- 既有失败（基线已存在）：<列出>
- 未覆盖范围：<明确写出>
```

## 输出

1. 基线记录。
2. 调用方反查表（含「确认不受影响」项）。
3. 改动级别判定与对应的验证要求。
4. 回归验证结论（与基线对比）。

## 质量门禁

- [ ] 改动**之前**记录了基线，且工作区当时是干净的
- [ ] 调用方反查表格包含「需同步修改」与「确认不受影响」两类结论
- [ ] 前后端两侧都查过（涉及字段或接口时）
- [ ] 改动级别已明确判定，拿不准时已往上靠一级
- [ ] 回归结果与基线对比，区分新增失败与既有失败
- [ ] 未覆盖范围已显式写出
- [ ] 契约类改动已同步 `docs/API_CONTRACT.md` 与两端类型定义

## 反模式

| 反模式 | 问题 |
| --- | --- |
| 不记录基线就动手 | 分不清既有失败与新增失败，责任无法界定 |
| 只列需要改的调用点 | 无法证明你真的查过全部调用方 |
| 用「已确认无影响」一句话代替表格 | 无证据的结论，评审无法核对 |
| 只跑新功能的测试 | 调用方既有功能静默失效 |
| 改公共方法不查调用方 | 影响面靠运气 |
| 回归结论只写通过项 | 隐藏未覆盖范围，评审误判风险 |
| 拿「覆盖率没降」当回归结论 | 覆盖率不反映业务语义是否仍正确 |
