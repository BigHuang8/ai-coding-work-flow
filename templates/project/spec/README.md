# 需求输入留档

本目录存放**一次需求的全部输入**，用于事后追溯「当初要求的是什么、我们打算怎么实现」。

## 命名与结构

```text
spec/<YYYYMMDD>-<主题>/
├── 需求与技术对照.md     主文档：原件清单、需求条目、技术实现对照、待确认项
├── 原始需求/             PRD 原件（docx / pdf / xlsx / md），只增不改
└── 原型/                 原型件与关键页面截图，只增不改
```

主题命名与 `docs/verification/<日期>-<主题>/` 保持一致，形成同一条追溯链。

## 创建方式

```bash
# 收到 PRD 或原型时
node scripts/new-spec.mjs --title "客户列表团队筛选" --with-artifacts --with-verification

# 口头需求，无正式文档
node scripts/new-spec.mjs --title "客户列表团队筛选"
```

轻量需求也可退回单文件形态 `spec/<YYYYMMDD>-<主题>.md`。

## 三条规则

1. **原件只增不改**。需求变更时另存新版本并在「原件清单」追加一行，不要覆盖旧版——否则无法解释需求为何变化。
2. **技术实现写在 `需求与技术对照.md`**，用 `R1`、`R2` 编号关联需求条目。不要把技术内容写回 PRD 原件，那会污染对外交付物。
3. **二进制原件旁留一份 markdown 转换件**（如 `PRD.md` 对应 `PRD.docx`）。AI 检索不到 `.docx` 里的内容；两者冲突时**以原件为准**。

## 各文件职责

| 文件 | 写什么 | 不写什么 |
| --- | --- | --- |
| `需求与技术对照.md` | 需求条目、验收标准、技术实现要点、影响文件、待确认项 | 完整需求正文以外的业务决策 |
| `原始需求/` | 外部交付的原件 | 任何内部结论 |
| `原型/` | 原型导出件与页面截图 | 实现截图（那属于验收证据） |

需求的**权威定义**在项目根目录的 `SPEC.md`；本目录是输入留档，不是需求权威来源。完整流程见 `docs/11-需求接收与拆解.md`。
